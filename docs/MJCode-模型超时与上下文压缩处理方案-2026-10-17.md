# MJCode 模型超时与上下文压缩处理方案

- 日期：2026-10-17
- 承接：`docs/MJCode-对话流程审查-2026-10-17.md`（对话流程问题清单）
- 触发：用户使用 `mimo-v2.6-flash` 时，长思考被 120s 看门狗强杀；随后一次 21 轮长任务在压缩 3 次后烧到 tokens 熔断，任务结束瞬间整个界面被崩溃页替换。
- 性质：施工单。本节所有"根因"都附代码行号或可复现探针，未验证项单列在 §6。

## 0. 结论摘要

三个问题不是并列的，它们串成一条链：

```
mimo 长思考 ──► T1 看门狗按「总时长」计时，120s 到点就杀
                        │
                        ▼（用户重试，历史更长）
               T2 压缩「看起来执行了、实际没压」，每轮仍全量重发
                        │
                        ▼（21 轮 × 77k ≈ 1.6M tokens，耗尽 600k 预算）
               C1 任务产出文件 ──► 渲染层缺一个 import ──► 整页崩溃
```

| 编号 | 问题 | 根因（一句话） | 证据 | 状态 |
|---|---|---|---|---|
| **T1** | mimo 一轮 >120s 必被杀 | `withTimeout` 是**总时长**计时器，不看流式进度 | 探针 A/B/C/D | 待修 |
| **T2** | 压缩 3 次，prompt 体积不降反升 | 尾部按**条数**保留（6 条）+ 切点**向后**推 → 末轮并发工具 ≥7 时直接放弃压缩；调用方不检查结果，照样清零窗口 | 探针 A/B/C | 待修 |
| **C1** | 任务结束瞬间"app 崩溃" | `MessageStream.tsx` 用了 `IconFile` 但未 import；`@ts-nocheck` 使类型检查失效；顶层 ErrorBoundary 把整页换成崩溃页 | crash jsonl 两条 `rendererError` | **已修** |
| **C2** | 崩溃只能靠"猜" | 无 `render-process-gone` / `unresponsive` 监听；无原生崩溃 dmp | 代码全仓 grep 为空 | 待补 |

## 2. T1：看门狗用错了秒表（P0）

### 2.1 代码事实

| 位置 | 内容 |
|---|---|
| `agent-core/index.js:1055` | `export const DEFAULT_MODEL_TIMEOUT_MS = 120000` |
| `agent-core/index.js:1066` | `withTimeout(promise, ms, label)`：`setTimeout` 固定计时，**不看流式进度**，也不可重置 |
| `agent-core/index.js:1524` | 整条 `chatWithRetry(...)` 被这一个 `withTimeout` 包住 |
| `main/main.js:565` | `AbortSignal.timeout(125000)`：**连 body 一起算**的绝对超时（不可撤销） |
| `agent-core/index.js:505` | `COMPACT_RESCUE_TIMEOUT_MS = 30000`（压缩救援只有 30s） |

推理模型（mimo）先出 `reasoning_content` 再出正文，思考期可能长时间没有"正文"，但**总时长**轻松破 120s → 必死。

### 2.2 探针证据

`desktop/scripts/probe-watchdog-semantics.mjs`（零依赖、不联网，把 120s 按 1/1000 缩小）：

| 场景 | 结果 |
|---|---|
| A 当前实现 + 持续有数据，总时长超阈值 | **122ms 被杀** |
| B 空闲语义 + 同一数据流 | 315ms 正常完成 |
| C 空闲语义 + 真挂起（无数据） | 121ms 被杀（反向用例） |
| D 空闲语义 + 无限流 | 502ms 被总量闸杀 |

结论：当前实现**只计总时长**。文案"`>120000ms 无响应`"在持续有数据时是错的。

> 探针首版把 C 写坏了（空闲计时被固定 interval 重置，C 拖到总量闸才被杀）。红/绿看不出问题，只有核对**耗时量级**才发现分支从未生效。改这个脚本必须复核 C 的耗时≈idleMs。

### 2.3 主流怎么算（2026-10-17 读取）

| 产品 | 计时语义 | 关键数字 |
|---|---|---|
| Claude Code | 首字节 / 流空闲 / 单请求总时长，三层 | `API_TIMEOUT_MS` 默认 **600000**；`CLAUDE_STREAM_IDLE_TIMEOUT_MS` 默认 **300000**（空闲）；首字节单独一层，且按请求体每 32KB 加 1s；每次重试有**独立**窗口 |
| Codex CLI | 流空闲 | `stream_idle_timeout_ms` 默认 **300000**；`request_max_retries` 4、`stream_max_retries` 5；社区还在提"再加一个 60s 首事件超时" |
| 火山引擎（国内推理模型实践） | 默认 30–60s 不够 | 建议 Agent 场景客户端超时 **≥30 分钟**，并改流式保持连接活性 |

共同点：**判断"卡死"看"多久没动静"，不是"总共花了多久"**；且 thinking chunk 必须计入进度。

### 2.4 方案：一只钟拆成三层

| 层 | 管什么 | 现值 | 建议 |
|---|---|---|---|
| 首字节 | 连上了但一个字不回（排队 / 网关缓冲） | 无 | **90s**，独立报错文案 |
| 空闲 | 已在出字，突然没动静 | 被总时长顶替 | **300s**（对齐主流） |
| 单轮总时长 | 无限流兜底 | 120s | **15min** |
| 压缩救援 | 做摘要那次调用 | 30s | **180s** |
| 重试 | 3 次共享 120s | 共享 | 每次重试**独立**窗口，均受总上限约束 |

设计原则：**等太久有用户手动停止兜底，杀太早没有任何补救**。所以超时宁可宽，配合"看得见在动"的 UI（已思考 N 秒 / 已收到 N 字）。

**实施方式**：三个数字落在 `desktop/main/streamGuard.js` 的 `DEFAULTS`；设置页「网络与超时」可改，落 `localStore.preferences['stream_timeouts']`，**每次请求现读、改完立即生效**。优先级：用户设置 > 环境变量（`MJ_STREAM_*`）> 内置默认。校验在主进程（越界收敛、非法值回落），保存后回显"生效值 + 来源"。

### 2.5 两个实现陷阱

1. **空闲检测不能用 read 循环内 bump**：真没数据时循环停在 `await reader.read()`，永远走不到 bump。必须外部 `setInterval` 比对 `lastByteAt`。
2. **`AbortSignal.timeout()` 不可撤销**：一旦创建管到 body 结束，首字节那层必须手写 `setTimeout` + `clearTimeout`，否则又退化成一个总时长。

另外：`reasoning_content`、`tool_calls` 分片、SSE 注释行（`:` 开头）都要算"有动静"，否则思考阶段仍被误判。

### 2.6 改动点

| 文件 | 改动 |
|---|---|
| `main/main.js:560-620` | 流读取循环加三层守卫，替换 `AbortSignal.timeout(125000)` |
| `agent-core/index.js:1055,1524` | 默认值改为粗兜底（15min），文案区分"无数据"与"总时长到顶" |
| `agent-core/index.js:505` | 压缩救援 30s → 180s |
| `renderer` | 思考阶段展示计时与已收字数（减少用户误按 Esc） |

## 3. T2：压缩"执行了但没压"（P0）

### 3.1 代码事实（三个缺陷叠加）

**缺陷 1：尾部按「条数」保留，不按「体积」**

`agent-core/index.js:682` → `const keepTail = aggressive ? 3 : 6;`

**缺陷 2：切点落在 tool 消息上时「向后」移动，极端情况移动到末尾就等于放弃**

`agent-core/index.js:649` `alignCutToRoundBoundary(body, cut)`：

```js
let k = Math.max(0, Math.min(cut, body.length));
while (k < body.length && body[k]?.role === 'tool') k += 1;   // 向后移
```

`cut = body.length - 6`。若最后一轮模型并发调用了 ≥7 个工具，末尾连续 tool 消息 ≥7 条 → 切点整体落在 tool 上 → 一路移到 `body.length` → `cut >= body.length` → **`return convo`（放弃压缩）**。

**缺陷 3：调用方不看结果，仍然清零窗口**

`agent-core/index.js:1613-1620`：

```js
if (gate === 'compact') {
  tokenRescues += 1;
  console.warn(`[agent] 上下文达模型窗口 ...，压缩后继续（第 ${tokenRescues}/3 次）`);
  convo = await compactHistory(convo, model, chatFn, { knownTokens: lastPromptTokens, force: true });
  tokenWindowSpent = 0;   // ← 不管压没压成，都清零
  continue;
}
```

压缩原样返回时：**摘要调用都没发生**（省不了 token），窗口却清零 → 再跑几轮又撞阈值 → 再"压缩"一次 → 21 轮里撞了 3 次，全是空转。附带 `lastPromptTokens` 在此分支未清空（`1520` 行的正常路径有清空），下一轮 `ctxEst` 可能沿用旧值。

### 3.2 探针证据

`desktop/scripts/probe-compact-noop.mjs`（构造 30 轮历史，仅改变最后一轮的工具并发数）：

| 场景 | 消息数 | 压缩前 | 压缩后 | 省下 | 实际动作 |
|---|---|---|---|---|---|
| A 末轮 3 个工具 | 122 | 82503 | 11511 | 70992 | ✅ 已压缩（摘要调用 1 次） |
| B 末轮 8 个工具 | 127 | 86563 | **86563** | **0** | ❌ 未压缩（摘要调用 **0** 次） |
| C 末轮 12 个工具 | 131 | 89814 | **89814** | **0** | ❌ 未压缩（摘要调用 **0** 次） |

A 证明压缩主路径本身是好的；B/C 证明**只要一轮里并发工具 ≥7 个，压缩必然放弃**。mimo 长任务里"一次读多个文件"是常态。

### 3.3 为什么线上表现为"越压越大"

第 1 次 90074、第 2 次 91713 —— 不是压缩把体积压大了，而是**压缩根本没改动历史**，这两轮都在按全价重发，期间又新增了工具结果。日志里的"压缩后继续"只表示"gate 判定为 compact"，**不表示压缩真的发生**。

### 3.4 连锁后果：预算语义被架空

- `tokenWindowSpent` 每次 compact 清零 → 预算 600k 变成"每窗口 600k"，实际累计烧到 **1,616,876** 才停。
- 21 轮 × ~77k prompt ≈ 全价重传同一批上下文，成本与延迟都被放大。
- 最终 `textLen=158`：21 轮重活干完，只输出 158 字，用户没有任何可读结果。

### 3.5 方案（已落地）

1. **尾部按 token 预算保留**：`keepTail` 由"条数"改为"保留最近 ≤ N tokens 的整轮"（常规 25% 窗口 / 激进 15%），并加"最多保留一半轮"的硬约束——否则紧窗口下预算 + 最少轮数会把整段都算成尾部，又退回 `cut=0`。
2. **切点方向修正**：改用 `tailCutByBudget()` 从尾部按轮累加，切点天然落在轮边界，不再需要"向后移动"这个会在末尾退化成"不压"的动作。
3. **调用方校验结果**：`if (convo !== beforeConvo)` 才清零窗口并清 `lastPromptTokens`；否则降级硬截断（`trimHistoryForRun`，保留最近 3 轮），硬截断也无收益则**挂起**（`kind:'tokens'`）而不是继续空转。
4. **兜底丢弃也改按轮**：原先按消息条数取 1/2 或 3/4，会切进工具轮中间产生孤儿 tool；现在按轮比例。
5. **抽公共 `groupRounds()`**：压缩与入口裁剪共用一份分组实现，防规则漂移。

1. **尾部按 token 预算保留**：`keepTail` 由"条数"改为"保留最近 ≤ N tokens 的整轮"（N 取窗口的 20–25%），保证压缩一定有余量。
2. **切点方向修正**：切点落在 tool 上时，应**向前**回退到该轮 `assistant` 之前（把这一整轮也纳入压缩区），而不是向后推到末尾。向后推的语义是"少压一点"，极端情况变成"不压"。
3. **调用方校验结果**：`if (compacted === convo)` → 判定为"压缩无收益"，此时**不得清零窗口**，并降级为硬截断（`trimHistoryForRun` 已有能力）或直接 `suspend-context` 提示用户新开会话。
4. **清空 `lastPromptTokens`**：压缩成功回写后置 `null`，与 `1520` 行保持一致。
5. **预算语义二选一并写明**：要么"窗口预算"（需在 UI 明确显示"本窗口/累计"两个数），要么"总预算"。现在日志打"累计 1616876"，用户会认为 600k 预算失效。

### 3.6 改动点

| 文件 | 改动 | 状态 |
|---|---|---|
| `agent-core/index.js` `groupRounds()` / `tailCutByBudget()` | 按轮分组 + 按体积取尾部（最多保留一半轮） | ✅ |
| `agent-core/index.js` `compactHistory` | 切点改用 `tailCutByBudget`；兜底丢弃改按轮比例 | ✅ |
| `agent-core/index.js` compact 分支 | 校验 `convo !== beforeConvo`；无收益→硬截断→挂起，**不再无条件清零窗口** | ✅ |
| `agent-core/index.js` `trimHistoryForRun` | 复用 `groupRounds`（去重） | ✅ |
| `desktop/test/compact-tail-budget.test.mjs` | 6 项：并发 3/8/12 工具都要压下来（>25%）、无孤儿 tool、无收益不清窗口、不再条数制 | ✅ |

**修复前后（探针 `probe-compact-noop.mjs`）**

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 末轮 3 个工具 | 82503 → 11511（省 70992） | 82503 → 40899（省 41604，50%） |
| 末轮 8 个工具 | 86563 → **86563（省 0）** | 86563 → 40061（省 46502，**54%**） |
| 末轮 12 个工具 | 89814 → **89814（省 0）** | 89814 → 40863（省 48951，**55%**） |

> 单看 A 反而"变差"了：旧实现的 A 是运气好（切点刚好在 assistant 上，切得极狠），
> 代价是 B/C 完全失效。新实现三档都在 50% 左右——**可预测比单点最优更重要**。

**变异验证**：把切点退回 `alignCutToRoundBoundary(body, body.length - 6)`，用例立刻在 B/C 变红（A 仍绿，说明断言精确指向该缺陷）；恢复后 6/6 绿。

### 4.2 为什么能存活

- `MessageStream.tsx:333` 使用 `<IconFile size={18} />`，但第 8 行的 import 列表里没有 `IconFile`（`icons/index.jsx:45` 明明已经导出）。
- 该文件首行是 `// @ts-nocheck` → `tsc --noEmit` 不检查未定义标识符 → **类型门禁失效**。
- 触发条件苛刻：只有消息里出现「输出文件卡片」（`RunOutputFiles`）才渲染这一行。平时不出现，长任务产出文件时才炸 —— 正好是这次 21 轮任务的收尾。

- 第一次：`components/MessageStream.tsx → ['IconFile']`（1 处）
- 修复后复核：**0 处**

### 4.4 修复

`renderer/src/components/MessageStream.tsx:8` 补 `IconFile` 到 import。已改，见 §7。

### 4.5 C2：可观测性缺口（已补）

**补之前的事实**：全仓搜不到 `render-process-gone` / `child-process-gone` / `unresponsive` 监听。渲染进程**进程级**崩溃（OOM、GPU、被杀）不留任何记录；窗口卡死也无感知；只有 JS 层异常能通过 `rendererError` 上报（这次正是靠它拿到证据）。

**现在的实现**（`main/lifecycle/crashGuard.js`）：

| 事件 | 处置 |
|---|---|
| `render-process-gone`（非 clean-exit） | 写诊断（kind + reason + exitCode + url + 活跃 runId + trace 尾部）→ 自动 `reload` 主窗口（会话在 local-data 里，不丢历史） |
| 同上，1 分钟内超过 3 次 | **停止自动重载**，只记录 `render-process-gone-loop` + 留通知。没有这道闸，一个必崩的渲染 bug 会变成无限重载把诊断文件刷满 |
| `child-process-gone` | 记录类型/原因/exitCode（GPU、utility、network）；clean-exit 不记，避免进程池收缩刷日志 |
| `unresponsive` | 只记录 + 留通知，**绝不重载**——重载等于把用户正在跑的任务杀掉 |
| `responsive` | 记录卡顿时长 |

**用户可见**：主进程保留通知队列，渲染层启动时通过 `app:crash-notice` 一次性领取（取完即清），toast 提示「界面刚刚自动重启过一次」/「反复崩溃已停止自动重启」。没有这条，用户只会觉得"闪了一下"，甚至怀疑数据丢了。

**门禁**：`test/crash-guard.test.mjs`（10 项，含"超限后不得再重载"的反向用例 + "attach 真的挂上了事件"的防空转断言）。
