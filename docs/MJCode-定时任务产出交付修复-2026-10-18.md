# 定时任务「跑不出 md 文档」修复报告（2026-10-18）

> 范围：仅 MJCode 桌面端定时任务通道。产出为代码 + 测试 + 本文档。
> 标注约定：**已验证** = 有可复现的验证证据；**默认假设** = 主理人裁决、可推翻；**未覆盖** = 明确没做。

---

## 1. 现象

用户建了一条定时任务：

```
名称：获取新闻
提示词：获取最新的100篇全球娱乐八卦新闻，输出一份md文档
计划：0 9 * * *（每天 09:00）
执行模型：跟随会话
```

结果：后台只有 5 条 TTFB 慢告警（每轮模型首字节 ~8s），**没有任何 md 产出**；任务卡片停在「运行中」；归档目录 `~/Documents/.MJCoder/tasks/获取新闻/2026-10-18.md` 里只有一段回答文本，没有文件。

---

## 2. 归因过程（含两次被我推翻的错误结论）

这一节刻意保留错误路径，因为**两次都差点被当成结论写进代码注释**。

### 2.1 错误结论一：以为是沙箱只读

初步看到 `main/main.js` 的：

```js
sandboxPolicy: cwd ? 'workspace-write' : 'read-only'
```

推断「cwd 为空 → 只读 → 写不了文件」。

**推翻**：`writeFile` 走 `runWriteTool` → `executeWriteTool` → Node `fs.writeFile`，**不经过 shell 沙箱**。`sandboxPolicy` 只约束 shell 子进程。真正决定能否落盘的是 `main/writeGuard.js` 的 `allowedWriteRoots({ cwd, userDataDir, tmpDir })`（只放行 cwd / userData / tmp）。

### 2.2 错误结论二：拿另一个任务的 trace 做错位归因

看到 `traces/scheduled_t-*.jsonl` 里 `verify_result.stats = {tools:5, writes:0}`，据此判断「模型 5 次工具调用、一次都没写文件」。

**推翻**：那条 trace 属于 **13:25 的「获取最新AI新闻10篇」成功任务**，不是失败的那个 100 篇任务。失败任务 `t-1792301283151-471` **没有 trace 文件**，`output:""` / `tools:0` 是 run 的**初始化值**（进程收尾前退出）——它是「未知」，不是「0 次」。

### 2.3 最终根因（已验证）

| 层 | 事实 | 证据 |
|---|---|---|
| 直接原因 | 定时通道的系统提示**只有**「产出精炼可读的结果摘要」，从没要求写成文件、也没给路径 | `agent-core/index.js` 的 `customSystemPrompt \|\| BASE_PROMPT` 是**整体替换** → BASE_PROMPT 里「你会用 write_file、默认在当前目录读写」整段丢失；对 10 条量级，写入条款还被「超过 10 条」卡住 |
| 结构性原因 | 没有任何机制能发现「用户要文件、模型只回文本」——交付判定只看「有没有工具调用 / 有没有自述未完成」 | `judgeRun` 前身只有 `detectUnfinished` + `detectExhausted`，两者都不看文件写入事实 |
| 放大原因 | 越界写不是快拒，而是等 **120s 审批超时** 后 deny；重试 5 次 = 10 分钟，直接撞单任务墙钟，死因被写成「执行超时」 | `approvalChannel` 的无人值守等待 120s；`runWriteTool` 缺省 `requireApproval: true` |
| 放大原因 | 进程退出后 run 永远停在 `running`，用户看到「一直运行中」，且拿不到任何结论 | `scheduler.loadStore()` 原先不收敛遗留 running |

**一句话**：不是模型不行，也不是权限不足，而是**产品把「产出」定义成一段聊天文本，且没有任何交付校验去对齐用户真正要的形态**。

## 3. 修复清单

### 3.1 产出落点与提示词

| 改动 | 文件 | 说明 |
|---|---|---|
| 产出目录 | `main/scheduledOutput.js` | `taskWorkDir` / `ensureTaskWorkDir`：`~/Documents/.MJCoder/output/<safeTaskDirName>/`；Documents 取不到时降级 `userData/output/`；复用既有 `safeTaskDirName`（Windows 保留名、`..`、60 上限、空名回落都覆盖），**只有一套命名规则** |
| cwd 一律产物目录 | `main/main.js` | 删掉 `schedModel.cwd \|\|` 短路；会话 cwd 只作为 `contextCwd` 写进提示词（可读不可写）。**这是有意的产品决策**：无人值守不应往用户项目里丢文件 |
| 产出契约 | `buildScheduledPrompt` | 5 条硬约束：必须写入指定目录（已建好不用 mkdir、别处会被立即拒）、建议文件名、回答只给「一句汇总 + 绝对路径」不贴正文、读从 contextCwd、失败如实说明 |
| 系统提示追加语义 | `agent-core/index.js`（+5 行） | 新增 `appendSystemPrompt`，`sysSections.base = BASE_PROMPT + append`，不再整体替换 |

### 3.2 交付校验（核心）

新建 `main/scheduledVerdict.js`（纯函数），判定链按强弱：

```
① 未完成（模型自述做不到 / 供应商拒答）        ← 措辞 + 拒答分类
② 引擎闸门（预算/轮次/上下文）                 ← 引擎事实
③ 零文件产出（writes==0 && shellWrites==0）    ← 确定性事实
④ 交付校验降级（V 层 L3 判不出/FLAG）          ← 概率判定，最后兜底
```

关键护栏（都是防**新的假失败**）：

- `writes` **或** `shellWrites` 任一 > 0 即算有产出（模型用 `cat > news.md` 写文件时只认 `writes` 会误判）
- 任一计数**未知**（null/NaN/无 verify 数据）→ 不判，宁可漏判也不误判
- 零产出排在交付降级**之前**：事实优先，避免用户看到「L3 判不出」这种不可行动文案
- 任务可用 `expects_file:false` 关闭该校验（只做 git 提交/只做汇报的任务），失败文案会直接告诉用户怎么关

### 3.3 状态与安全

| 改动 | 说明 |
|---|---|
| 僵尸 run 收敛 | `loadStore()` 后把遗留 `running` 标为 failed，`tools = null`（**不再假装「0 次工具调用」**），文案「工具调用与输出未收尾，本次数据不可信」 |
| 越界写快拒 | 定时通道写工具 `requireApproval:false` → 白名单内直接执行、白名单外**立即**结构化失败（实测 7ms，原 120s） |
| 危险 shell 快拒 | `unattended` 标记 + `unattendedApproval` 审批终结器 → 立即 deny 并说明「无人值守，没有人在场」（实测 8ms） |
| 无人值守 = 显式入参 | `scheduledToolHandlers({ unattended, contextCwd })`；交互式不传 → **保留原有审批行为**（这条是终验抓到的回归） |
| 项目内任务不失效 | `contextCwd` 只兜底读类与 `git_*`，写工具与 shell 不注入 → git 任务不会在产物目录里报 `fatal: not a git repository` |
| 可观测 | 定时运行 `onTrace` 落盘（`appendTraceEvent(runId, evt)`）、`run.workDir` 落运行记录 |

### 3.4 参数

| 参数 | 原值 | 新值 | 理由（默认假设，可推翻） |
|---|---|---|---|
| `maxRounds` | 20 | 40 | 100 篇 ≈ 10 批 ×（抓取+落盘）≈ 20 轮，原值零余量 |
| `tokenBudget` | 200000 | 400000 | 按每轮 ~15k prompt 估算，200k 约 13 轮见底；交互通道是 600k，定时取 400k 属保守 |

### 4.2 终验抓到的回归（已修）

改动经共享工具表泄漏到交互式会话：对话里 `sudo` 由「3025ms 弹审批卡」变成「6ms 被无人值守拒绝」——**人就在屏幕前也无法批准**。

改为显式入参 `scheduledToolHandlers({ unattended, contextCwd })` 后复验（同一对照脚本）：

| 场景 | 泄漏时 | 修复后 |
|---|---|---|
| 交互式 `sudo -n true` | 6ms 拒绝，审批请求 0 次 | **3016ms 走审批**，请求 0→1 |
| 交互式越界写 | 6ms 硬拒 `outsideWhitelist` | **3013ms 弹卡**，请求 1→2，文件未创建 |
| 定时侧危险 shell | — | **14ms** deny、含「无人值守」、审批 0 次 |
| 定时侧越界写 | — | **7ms** `blocked+outsideWhitelist`，文件未创建 |
| 定时侧界内写 | — | **15ms** 真落盘，success / writes=1 |

### 4.3 一次「假修复」及其教训

D1（git/读类 cwd）第一次修复在**单元测试里是绿的、真实链路里是红的**：`git_status` 仍报 `fatal: not a git repository`。

- 根因：`agent-core` 对 CWD_TOOLS **无条件注入**宿主 cwd（= 产物目录），而实现写成 `args.cwd || ctxDir` → `ctxDir` 永远是死代码。
- 更值得记的：新测试里有一条把「模型显式 cwd 优先」写成了**期望值**，等于把 bug 编码成了规范。单元测试越绿，真实链路的失败越没人发现。

修法：改为 `ctxDir || args.cwd`；门禁换成**过真实 `runAgent` 循环**（真 git 仓库 + 真工具），并做**变异验证**——把修复回退后门禁必须变红：

```
[FAIL] 真实链路：git_status 在项目里执行 — {"stderr":"fatal: not a git repository …"}
[FAIL] 真实链路：read_file 的相对路径读到项目文件 — 读不到（落到了 output-dir）
scheduled-context-cwd: 1/3
```

恢复后 3/3。**判据：门禁若不能在生产调用形态下变红，它就不是门禁。**

### 7.1 结论

> 以当前代码重跑「获取100篇娱乐八卦新闻，输出一份md文档」：**最可能成功落盘**
> —— md 在 `~/Documents/.MJCoder/output/获取新闻/`，`writes ≥ 1`，`status = success`，归档追加到 `tasks/获取新闻/<date>.md`。
>
> 次可能是**诚实失败**：抓取被反爬/限流后反复重试烧完 40 轮或 400k → `failed`「引擎报告任务未完成…已产出部分结果」，半成品仍在产出目录。
>
> **不会再出现「显示成功但找不到 md」。**

### 7.2 终验后补的两条（S-1 / S-2，已完成）

| 项 | 问题 | 处理 |
|---|---|---|
| S-1 | 读写相对路径落点不同：`write_file('news.md')`→产出目录，`read_file('news.md')`→项目目录（notFound）。BASE_PROMPT 要求「改完回读验证」，模型会白烧一轮 | 契约补「回读用绝对路径」；`readFile`/`listDir` 改为 `withRead` 双根解析（判据是 `existsSync`，**不是**「notFound 就重试」——后者会把「目录确实为空」误判成未命中，也会把权限错误吞成文件不存在） |
| S-2 | `contextCwd` 不校验存在性：项目被删/移动后 git 与读类全指向不存在路径 | `scheduledRunContext` 做 `existsSync`，不存在按空上下文处理并 warn；产出目录不受影响（项目没了也要能落盘）|

验证：`scheduled-context-cwd` 5/5（含「写完立刻用相对路径回读能读到」「两处都没有仍返回 notFound」「写工具绝不写进用户项目」三条）、`scheduled-workspace` 25/25（含 S-2 的降级与留痕）。
