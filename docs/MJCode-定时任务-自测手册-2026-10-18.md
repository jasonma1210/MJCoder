# 定时任务：清单执行 / 对外开关 / 事件触发 —— 自测手册（2026-10-18）

> 这一版补齐了第三轮审查记的三条「未覆盖项」。三项都已落地代码 + 单测，
> 但**没有在 Electron 真机里跑过**，所以下面每一步都是给你自己验的。
> 每步都写清：怎么造场景、**预期看到什么**、以及「看不到就说明哪里坏了」。

---

## 0. 前置

```bash
cd desktop && npm start          # 或你的常规启动方式
```

三个前置条件，缺一个现象就不成立：

1. 会话里先选一个模型（定时任务复用它和凭证）。
2. 任务要有 `cwd`（工作目录）—— 重放与对外拦截都按它判断，没有 cwd 的任务看不到拦截效果。
3. 别用「只读汇总」类任务验证第 1 项（它本来就不产生对外动作）。

## 1. 对外动作开关（`external_policy`）

### 1.1 默认拦截

1. 新建任务，提示词写：
   > 在 cwd 下创建一个 a.txt，内容随便，然后 git add a.txt && git commit -m "test from scheduled"
2. **不要**打开「允许对外动作」（默认关）。保存。
3. 点「立即运行」。

**预期**：
- 运行结束，卡片出现 `待确认 1 项`。
- 点「运行历史」→ 该次运行下有「待确认动作（1 项）」，里面是 `git_commit · git commit -m "test from scheduled"`，按钮是「执行」。
- `~/Documents/.MJCoder/tasks/<任务名>/<今天>.md` 末尾有：
  ```
  ### 待确认动作（1 项，本次未执行）
  1. `git_commit`：`git commit -m "test from scheduled"`
  ```
- **仓库里没有新 commit**（`git log -1` 还是原来那条）。

> 看不到拦截 → 检查任务 `external_policy` 是不是被写成 `allow`；以及 `main/scheduledGuard.js` 的 BLOCKED 表里有没有 `gitCommit`。

### 1.2 打开放行

1. 同一任务，点卡片上的「对外：拦截」按钮 → 弹二次确认 → 确认。
2. 再点「立即运行」。

**预期**：按钮变成红色「对外：放行」；这次 `git commit` 真的执行了（`git log -1` 能看到）；不会产生待确认项。

> 注意：放行后**不再有清单**，这是设计（用户显式承担了无人值守写外部系统的风险）。

## 1.5 任务级模型 + 记住「上次用过的模型」（2026-10-18 补）

### 1.5.1 任务里单独选模型

新建任务时，**提示词输入框下面**多了一个下拉：

- 默认「跟随会话当前模型」= 旧行为
- 选具体模型 = 这个任务**固定用它跑**，你在会话里切模型不会把它带跑
- 卡片上会显示 `模型：xxx`

**验证**：
1. 建两个任务，一个选模型 A、一个不选；会话里切到模型 B。
2. 分别「立即运行」。
3. 预期：A 那条的日志里用的是 A；不选的那条用 B。

> 若 A 那条仍用 B → 检查 `scheduler.runTask` 的 `normalizeTaskModel(t.model) || execCtx.model` 是否被改回。

### 1.5.2 记住上次使用的模型

以前每次启动都会回到「第一个供应商的第一个模型」。现在会把**最后一次真正用过的模型**记在本地。

**验证**：
1. 在会话里切到一个非默认模型。
2. 完全退出应用，重开。
3. 预期：仍是那个模型（模型选择器显示的就是它）。

> 模型或供应商被删掉时会自动回落到第一个可用模型 —— 这是有意的，不报错。

### 1.5.3 已有任务改模型（2026-10-18 补）

任务卡片上、cron 那行下面多了一行「执行模型 + 下拉」。改完**立刻保存，下一轮执行就用新模型**，不用删了重建。

- 选「跟随会话」= 清掉任务级模型（显式发 `model: null`，不是"没传"）
- 下拉里括号是窗口：`deepseek-v4 (512k)`；**带 `~` 的是估算值**（模型没声明窗口，按表兜底）

**验证**：
1. 把那条「新闻获取」从「跟随会话」改成某个具体模型。
2. 完全退出应用、重开 → 预期下拉仍是那个模型（快照已落盘）。
3. 再改回「跟随会话」→ 重启后仍是「跟随会话」（这条最容易坏：`null` 被当成"没传"就会改不掉）。

> 若改回「跟随会话」重启后又变回具体模型 → 检查 `scheduled:save` 里是否用的是
> `Object.prototype.hasOwnProperty.call(p, 'model')` 判定，而不是 `p.model != null`。

### 1.5.4 窗口口径：估算值会带 `~`（2026-10-18 修正）

映射表里没有的自建模型一律按 32k 兜底，但**兜底值不等于真实值**（主理人实测自己的模型最低 512k）。
所以现在：未声明的窗口在下拉里显示为 `~32k`，并在新建表单里给一条提示引导去声明真实值。

**验证**：
1. 新建任务，选一个自建供应商的模型（不在映射表里）。
2. 预期：下拉里是 `~32k` 而不是 `32k`；表单下方出现「上下文窗口未声明…」的提示。
3. 去「模型设置 → 上下文窗口」选 512K（这个档位是本轮新增的），回到定时任务再选同一模型。
4. 预期：显示 `512k`（无 `~`），提示消失。

## 2. 清单的一键执行（重放）
接 1.1 的状态（有一条 pending 的 `git_commit`）。

### 2.1 正常重放

点那条的「执行」。

**预期**：
- 状态从「待确认」变成「已执行」（`action_executed`）。
- `git log -1` 出现那条 commit。
- 卡片上的「待确认 N 项」减少（或消失）。

### 2.2 幂等（重点）

**同一个动作再点一次**（或快速双击）。

**预期**：第二次直接失败并提示「该动作已处理过（同一动作不能执行两次）」，**不会产生第二个 commit**。

### 2.3 过期（stale）—— 这条最能说明设计意图

1. 让任务再产生一条 pending 的 `git_commit`（跑一次 1.1）。
2. **在外部手动提交一次**（`git commit --allow-empty -m "someone else"`），让 HEAD 变化。
3. 回到 UI，点那条待确认项的「执行」。

**预期**：失败，状态「已过期」，提示
`工作区已变化（HEAD xxxxxxx → yyyyyyy），请重跑任务而不是直接重放`。

> 这条是「审批 ≠ 永久豁免校验」。如果它照样执行了，说明 `scheduledReplay.js` 里的 HEAD 校验被绕过了 —— 那会在真实场景里把别人后来的改动一起提交掉。

### 2.4 不可重放的动作

让任务调一个 MCP 工具（例如让模型调用任意已连接的 MCP 写入工具）。

**预期**：清单项显示「需人工」，**没有「执行」按钮**。

> 设计理由：MCP/PR 依赖原始会话与鉴权上下文，盲目重放等于绕开原来的授权路径。

## 3. 事件触发

### 3.1 建一个事件任务

1. 新建任务，打开「由外部事件触发」。
2. 来源填 `github`，事件名填 `pr_opened`。
3. 提示词写：`把本次事件写进一句话摘要，不要调用任何工具。`
4. 保存 → 卡片上应显示 `事件：github/pr_opened`（不再显示 cron）。

### 3.2 起事件入口

**默认不监听**，必须显式给端口：

```bash
cd desktop
MJ_SCHEDULED_EVENT_PORT=47615 MJ_SCHEDULED_EVENT_TOKEN=dev npm start
```

启动日志里会有：
```
[scheduled] 事件入口已监听 127.0.0.1:47615（POST /event，token=dev）
```

### 3.3 投递事件

```bash
# 正常投递
curl -s -XPOST 127.0.0.1:47615/event \
  -H 'x-mj-token: dev' -H 'content-type: application/json' \
  -d '{"source":"github","event":"pr_opened","id":"pr-42"}'
# 预期：{"ok":true,"eventId":"pr-42","matched":1,"started":1,"skipped":[]}
```

**预期**：任务立刻开始跑（不等 cron），运行记录里 trigger 显示 `event`。

### 3.4 去重（重点）

**同一条 curl 再发一次。**

**预期**：`{"ok":true,...,"started":0,"skipped":[{"id":"t-...","reason":"duplicate"}]}`，
任务**不会**再跑一次。

### 3.5 合并

任务还在跑的时候，把 `id` 换一个再发。

**预期**：`skipped:[{"reason":"busy"}]`，不会排队（排队会让同一个 PR 的三条事件把同一件事做三遍）。

### 3.6 安全边界

```bash
# 不带 token
curl -s -o /dev/null -w '%{http_code}\n' -XPOST 127.0.0.1:47615/event -d '{}'
# 预期：401

# 错误路径
curl -s -o /dev/null -w '%{http_code}\n' -XPOST 127.0.0.1:47615/other -H 'x-mj-token: dev'
# 预期：404
```

另外确认：`lsof -nP -iTCP:47615 -sTCP:LISTEN` 的地址必须是 `127.0.0.1:47615`，**不能是 `*:47615`**。

## 4.5 任务太大怎么办（引擎自动拆分，不用你写批处理）

**你只需要写「获取 100 条 AI 新闻」，拆分由引擎和模型自己做。** 三层兜底：

| 层 | 谁在做 | 行为 |
|---|---|---|
| ① 提示词策略 | 定时通道 system prompt | 遇到枚举/抓取 >10 条时，模型**自动分批**（每批 ≤10，写完即弃原文） |
| ② 自动换新窗口 | 引擎 | 上下文压不动（压缩+硬截断都无收益）时，用**台账交接**重建精简上下文继续跑，最多 2 次 |
| ③ 如实收尾 | 引擎 | 2 次续跑仍不够 → 判失败并说明「已自动续跑 2 次仍不够」，附建议（分批/换大窗口模型） |

**验证①**：建一个「获取 100 条 AI 新闻」的任务（模型选 32k 窗口的），跑完看归档 md——
应该是**分段写入**的（每批 10 条），而不是等到最后一次性写。

**验证②**：日志里出现
`[agent] 上下文压不动 → 自动换新窗口续跑（第 1/2 次），交接 N 条台账`
随后任务继续跑（而不是直接结束）。运行记录里能看到 `auto_restart` 痕迹。

**验证③**：如果两次都不够，卡片会显示
「已自动换新窗口续跑 2 次仍不够，继续跑只会空转。请把任务拆小…」——这是真实的失败，
不是假成功（状态是失败，且会计入连续失败 → 3 次后自动暂停任务）。

> 仍然建议：**枚举量大的任务配一个大窗口模型**（128k）。自动续跑是兜底，不是免费的——
> 每次重启都要重读一遍任务上下文。

## 5. 常见失败怎么读（2026-10-18 补）
运行失败时，`run.error` 现在是「人话提示 + 原始错误」两段。四种常见形态：

| 你看到的提示开头 | 真实原因 | 怎么办 |
|---|---|---|
| 模型服务商以「内容安全」拒绝了这次请求 | 图片/新闻/网页**原文**触发了对端输入过滤（不是程序 bug，且内容相关 → 昨天能跑今天不能是正常的） | 把条数从 100 降到 20–30、缩小主题、或换模型/供应商 |
| 上下文超出模型窗口 | 单次抓太多，历史把窗口顶满 | 降低抓取量，或换窗口更大的模型 |
| 供应商限流或额度不足 | 429 / 配额 | 稍后重试或查配额 |
| 模型凭证失效或权限不足 | 401/403 | 重新填 API Key |

**判定「是模型还是软件」的 1 分钟办法**：把同一个任务换一个供应商的模型再跑一次
（定时任务复用会话模型，在会话里切换即可）。换了就好 → 是模型侧策略；换了还一样 → 回来找我。

> 抓取类任务（「100 条新闻」这种）最容易撞第一条。写法建议：**分批落盘**
> ——「分 5 批、每批 20 条，每批写进文件后丢弃原文再继续」。既压上下文，也压触发过滤的概率。

## 7. 存储被写空怎么救（2026-10-18 数据丢失事故）

### 7.1 事故现场（这次真的发生了）

你截图看到「我创建的定时任务不显示了」，磁盘上是这样的：

| 文件 | 大小 | 内容 |
|---|---|---|
| `scheduled-tasks.json` | 31 B | `{"tasks":[],"runs":[]}` |
| `scheduled-tasks.json.bak` | 2851 B | 1 个任务（新闻获取）+ 2 条运行记录 |
| 两者 mtime | 相同 | → 说明是**同一次写盘**里发生的「先备份、再写空」 |

### 7.2 根因（为什么"合法空库"比"文件损坏"更可怕）

```
第二个实例启动
  → requestSingleInstanceLock() 失败
  → app.quit()
  → 顶层注册的 will-quit 照样执行
  → scheduler.persist()  ← 此时 store 还是模块初始化值 {tasks:[],runs:[]}
      ├─ 先把旧文件复制成 .bak（数据活下来了，这是唯一幸存副本）
      └─ 再把空 store 原子写入主文件
  → 下次启动 loadStore() 读到 **合法 JSON** → 不走"损坏"分支 → 零告警
```

`local-data.json`（2.7 MB）当时**没被清空**，纯属结构上的巧合：`localStore.flushSync()`
有 `if (!this._dirty && !this._flushTimer) return` 守卫，第二实例什么都没改所以直接返回。
`persist()` 没有这层守卫。

### 7.3 修了三层

| 层 | 位置 | 行为 |
|---|---|---|
| ① 总开关 | `main/main.js` 的 `will-quit` | 抢锁失败的实例首行 `if (!hasMainLock) return;` —— 不参与任何退出落盘 |
| ② 模块守卫 | `main/scheduler.js` 的 `persist()` | 未 `loadStore()` 前调用一律拒绝写盘并返回 `{ok:false,error:'store_not_loaded'}` |
| ③ 自救 | `main/scheduledStore.js` | 主文件损坏 → 自动从 `.bak` 恢复并回写；主文件合法但为空 → 给 UI「可恢复」提示 |

### 7.4 验证（这三条都要自己跑一遍）

**A. 第二实例不再清空数据**

```bash
# 1) 先确保有一个任务
# 2) 应用已经在运行的情况下，再启动一次
cd desktop && npx electron .
# 3) 预期：新实例立刻退出（聚焦已有窗口），scheduled-tasks.json 的 mtime 不变
ls -la ~/Library/Application\ Support/mj-code-desktop/scheduled-tasks.json
```

**B. 已丢的数据怎么回来**

界面上会出现红色横幅：`定时任务存储被清空，备份里还有 N 个任务` + 「恢复」按钮。
点它即可（主进程覆盖前会另存 `.before-restore-<ts>`，恢复本身也能反悔）。

**C. 主文件真损坏时不静默**

```bash
D=~/Library/Application\ Support/mj-code-desktop
cp "$D/scheduled-tasks.json" /tmp/keep.json
printf '{"tasks": [ {"id":"t-1","na' > "$D/scheduled-tasks.json"   # 造半写残留
# 重启应用 → 预期：任务还在（从 .bak 恢复）+ 目录下多出 scheduled-tasks.json.corrupt-<ts>
ls "$D" | grep corrupt
```

### 7.5 单元测试对应

`test/scheduled-store-guard.test.mjs`（8 条）：

| 用例 | 守的是什么 |
|---|---|
| 未加载即写盘必须拒绝 | 事故根因，磁盘一个字节都不能动 |
| 损坏 + 好备份 → 自动恢复并回写 | 不静默以空库开工 |
| 合法但为空 + 备份有货 → 只提示 | 不自动恢复（否则会把"删掉最后一条"撤销掉） |
| `cleared_at` 标记 → 不提示 | 用户主动清空 ≠ 数据丢失 |
| `restoreBackup()` 正常 / 无备份 | 一键恢复与失败兜底 |
| 加载后正常写盘 | 证明守卫没把正常路径堵死（**正样本**） |
| `main.js` will-quit 被 `hasMainLock` 闸住 | 源码断言：这条守卫被删掉时会红 |

> 反向验证已做：删掉 `storeLoaded` 守卫与 `will-quit` 的 `hasMainLock` 判断后，恰好这两条用例转红（6/8），
> 说明它们是承重的，不是哑校验点。

## 8. 侧栏一级导航的选中态（2026-10-18 修）

**你报的现象**：点「定时任务」页面跳对了，但左侧那一项没有变成选中样式。

**两个真因，缺一都会复现**：

| # | 真因 | 修法 |
|---|---|---|
| ① | 只有「新建会话」传了 `active`，判据还是 `!activeThread` —— 定时任务页没有打开会话，该亮不亮；一旦有会话又可能两个一起亮（不互斥） | 新增 `lib/navState.ts` 的 `activeNavOf()`：互斥且穷尽（scheduled / ecosystem / new / 均不亮），穷举 16 种组合单测 |
| ② | 选中样式是 `bg-hover`，**与 hover 同色** —— 就算 `active` 传对了，视觉上也等于没选中 | 换成 theme.css 里本来就为「当前选中项」准备的专用令牌 `bg-select-bg` + `text-select-fg`（此前零引用），并补 `aria-current="page"` |

**验证**：
1. 点侧栏「定时任务」→ 该项应为淡蓝底 + 蓝字，另两项正常。
2. 点「新建会话」→ 高亮回到新建会话，定时任务不再亮。
3. 打开一个会话 → 三项都不亮（会话态不属于一级导航）。
4. 打开「生态中心」→ 生态中心亮；此时再进定时任务 → 定时任务优先。

> 自动化：`test/sidebar-nav-active.test.js`（10 条，含 16 组合穷举 + 连线契约 + 选中态令牌）；
> 渲染层 Playwright 另验「有且只有一个 `aria-current=page`、且选中项底色非透明」。
> 变异验证过：把判据改回「有会话就压过定时任务」、把 token 换回 `bg-hover`，对应断言都会红。
