# 定时任务：清单执行 / 对外开关 / 事件触发 —— 自测手册（2026-10-18）

> 这一版补齐了第三轮审查记的三条「未覆盖项」。三项都已落地代码 + 单测，
> 但**没有在 Electron 真机里跑过**，所以下面每一步都是给你自己验的。
> 每步都写清：怎么造场景、**预期看到什么**、以及「看不到就说明哪里坏了」。

---

## 0. 前置

```bash
cd desktop && npm start          # 或你的常规启动方式
```

三个前置条件，缺一个现象就不成立：

1. 会话里先选一个模型（定时任务复用它和凭证）。
2. 任务要有 `cwd`（工作目录）—— 重放与对外拦截都按它判断，没有 cwd 的任务看不到拦截效果。
3. 别用「只读汇总」类任务验证第 1 项（它本来就不产生对外动作）。

## 1. 对外动作开关（`external_policy`）

### 1.1 默认拦截

1. 新建任务，提示词写：
   > 在 cwd 下创建一个 a.txt，内容随便，然后 git add a.txt && git commit -m "test from scheduled"
2. **不要**打开「允许对外动作」（默认关）。保存。
3. 点「立即运行」。

**预期**：
- 运行结束，卡片出现 `待确认 1 项`。
- 点「运行历史」→ 该次运行下有「待确认动作（1 项）」，里面是 `git_commit · git commit -m "test from scheduled"`，按钮是「执行」。
- `~/Documents/.MJCoder/tasks/<任务名>/<今天>.md` 末尾有：
  ```
  ### 待确认动作（1 项，本次未执行）
  1. `git_commit`：`git commit -m "test from scheduled"`
  ```
- **仓库里没有新 commit**（`git log -1` 还是原来那条）。

> 看不到拦截 → 检查任务 `external_policy` 是不是被写成 `allow`；以及 `main/scheduledGuard.js` 的 BLOCKED 表里有没有 `gitCommit`。

### 1.2 打开放行

1. 同一任务，点卡片上的「对外：拦截」按钮 → 弹二次确认 → 确认。
2. 再点「立即运行」。

**预期**：按钮变成红色「对外：放行」；这次 `git commit` 真的执行了（`git log -1` 能看到）；不会产生待确认项。

> 注意：放行后**不再有清单**，这是设计（用户显式承担了无人值守写外部系统的风险）。

## 2. 清单的一键执行（重放）

接 1.1 的状态（有一条 pending 的 `git_commit`）。

### 2.1 正常重放

点那条的「执行」。

**预期**：
- 状态从「待确认」变成「已执行」（`action_executed`）。
- `git log -1` 出现那条 commit。
- 卡片上的「待确认 N 项」减少（或消失）。

### 2.2 幂等（重点）

**同一个动作再点一次**（或快速双击）。

**预期**：第二次直接失败并提示「该动作已处理过（同一动作不能执行两次）」，**不会产生第二个 commit**。

### 2.3 过期（stale）—— 这条最能说明设计意图

1. 让任务再产生一条 pending 的 `git_commit`（跑一次 1.1）。
2. **在外部手动提交一次**（`git commit --allow-empty -m "someone else"`），让 HEAD 变化。
3. 回到 UI，点那条待确认项的「执行」。

**预期**：失败，状态「已过期」，提示
`工作区已变化（HEAD xxxxxxx → yyyyyyy），请重跑任务而不是直接重放`。

> 这条是「审批 ≠ 永久豁免校验」。如果它照样执行了，说明 `scheduledReplay.js` 里的 HEAD 校验被绕过了 —— 那会在真实场景里把别人后来的改动一起提交掉。

### 2.4 不可重放的动作

让任务调一个 MCP 工具（例如让模型调用任意已连接的 MCP 写入工具）。

**预期**：清单项显示「需人工」，**没有「执行」按钮**。

> 设计理由：MCP/PR 依赖原始会话与鉴权上下文，盲目重放等于绕开原来的授权路径。

## 3. 事件触发

### 3.1 建一个事件任务

1. 新建任务，打开「由外部事件触发」。
2. 来源填 `github`，事件名填 `pr_opened`。
3. 提示词写：`把本次事件写进一句话摘要，不要调用任何工具。`
4. 保存 → 卡片上应显示 `事件：github/pr_opened`（不再显示 cron）。

### 3.2 起事件入口

**默认不监听**，必须显式给端口：

```bash
cd desktop
MJ_SCHEDULED_EVENT_PORT=47615 MJ_SCHEDULED_EVENT_TOKEN=dev npm start
```

启动日志里会有：
```
[scheduled] 事件入口已监听 127.0.0.1:47615（POST /event，token=dev）
```

### 3.3 投递事件

```bash
# 正常投递
curl -s -XPOST 127.0.0.1:47615/event \
  -H 'x-mj-token: dev' -H 'content-type: application/json' \
  -d '{"source":"github","event":"pr_opened","id":"pr-42"}'
# 预期：{"ok":true,"eventId":"pr-42","matched":1,"started":1,"skipped":[]}
```

**预期**：任务立刻开始跑（不等 cron），运行记录里 trigger 显示 `event`。

### 3.4 去重（重点）

**同一条 curl 再发一次。**

**预期**：`{"ok":true,...,"started":0,"skipped":[{"id":"t-...","reason":"duplicate"}]}`，
任务**不会**再跑一次。

### 3.5 合并

任务还在跑的时候，把 `id` 换一个再发。

**预期**：`skipped:[{"reason":"busy"}]`，不会排队（排队会让同一个 PR 的三条事件把同一件事做三遍）。

### 3.6 安全边界

```bash
# 不带 token
curl -s -o /dev/null -w '%{http_code}\n' -XPOST 127.0.0.1:47615/event -d '{}'
# 预期：401

# 错误路径
curl -s -o /dev/null -w '%{http_code}\n' -XPOST 127.0.0.1:47615/other -H 'x-mj-token: dev'
# 预期：404
```

另外确认：`lsof -nP -iTCP:47615 -sTCP:LISTEN` 的地址必须是 `127.0.0.1:47615`，**不能是 `*:47615`**。

## 4. 顺手修的一个真 bug（也请验一下）

**启用/停用开关之前是点了没反应的**：UI 只发 `{ id, enabled }`，而 `scheduled:save` 要求
名称/提示词/cron 三件套必填 → 边界直接拒绝，错误还被 UI 吞掉。
现在改成了部分更新（带 id 时只校验实际提供的字段）。

**验证**：随便点一个任务的开关 → 立即变灰/变亮并持久化（重启后仍是该状态）。
之前的表现是：点了闪一下又变回去，控制台无报错。
