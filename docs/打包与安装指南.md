# MJ Coder 打包与安装指南

> 适用：`desktop/`（Electron 33 + electron-builder 25.1.8 + electron-updater）
> 关联文档：《发布回滚Runbook.md》（发版/回滚）、《签名公证更新演练Runbook.md》（签名/公证/更新）
> **纪律（与两份 Runbook 一致）**：对外分发的正式包只从 CI 产出；本地打包用于自测、内测分发、问题复现。

## 0. 30 秒速查

| 我想要 | 命令（在 `desktop/` 下） | 产物落在 `release/` |
|---|---|---|
| macOS 安装包（当前机器架构） | `npm run dist:mac` | `MJCode-<v>-mac-<arch>.dmg` + `.zip` |
| macOS 双架构（Intel 也能装） | `npx electron-builder --mac --universal` | 同上，arch = `universal` |
| Windows 安装包 | `npm run dist:win` | `MJCode-<v>-win-<arch>.exe`（NSIS） |
| Linux 安装包 | `npm run dist:linux` | `MJCode-<v>-linux-<arch>.AppImage` |
| 只验配置、不产安装包（最快） | `npm run dist:dir` | `release/mac-arm64/MJ Coder.app` |
| 三个平台全要 | **走 CI**（打 tag），见第 9 节 | GitHub Actions Artifacts |

> `dist:mac / dist:win / dist:linux / dist:dir` 是本次新增的快捷脚本，等价于
> `npm run build --prefix renderer && electron-builder --<platform>`。

## 1. 交叉编译：哪个平台能打出哪个包

| 构建机 ↓ / 目标 → | macOS | Windows | Linux |
|---|---|---|---|
| **macOS** | ✅ 原生（arm64 / x64 / universal） | ⚠️ 需装 wine，且不稳定 | ❌ 不保证（AppImage 工具链是 Linux 二进制） |
| **Windows** | ❌ 不支持 | ✅ 原生（x64 / arm64） | ❌ 不支持 |
| **Linux** | ❌ 不支持 | ⚠️ 需 wine | ✅ 原生（x64 / arm64） |
| **GitHub Actions** | ✅ macos runner | ✅ windows runner | ✅ ubuntu runner |

**结论：要哪个平台的包，就在哪个平台打。** 手头只有 Mac 却要 Windows 包时，优先用 CI（第 9 节），其次本机 `brew install --cask wine-stable` 后应急构建（能出包，但 NSIS 偶发失败）。
Linux 包在本机可走 Docker：

```bash
docker run --rm -v "$PWD":/project -w /project electronuserland/builder:latest \
  npx electron-builder --linux
```

## 2. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| Node | **22.x**（CI 与实测环境） | 低于 18 会因 Electron 33 的包约束报错 |
| npm | 10.x | 仓库使用 `package-lock.json`，用 `npm ci` 可复现 |
| 首次装依赖 | `cd desktop && npm ci && cd renderer && npm ci` | desktop 与 renderer 是**两个** node_modules |
| macOS 签名（可选） | Xcode Command Line Tools + Developer ID 证书 | 不签名也能出包，见第 7 节 |
| Windows 目标（在 mac 上） | `brew install --cask wine-stable` | 仅 NSIS 需要 |
| 磁盘 | 单平台 400MB–1GB | `release/` 会留全部中间产物，可安全删除 |
| 图标 | `renderer/src/assets/logo.png`，当前 **2048×2048** | electron-builder 要求 ≥512×512 |

## 3. 一条命令背后的三步

```
npm run dist:mac
├─ npm run build --prefix renderer   → renderer/dist/（Vite 产物）
├─ electron-builder --mac            → release/mac-arm64/MJ Coder.app（未压缩可执行）
└─                            dmg    → release/MJCode-<v>-mac-<arch>.dmg
```

**两个必知陷阱**

1. **不要跳过 renderer 构建**。`build.files` 是白名单，只收 `renderer/dist/**`——
   直接跑 `npx electron-builder` 会把**上一次**的 dist 打进安装包，改了 UI 却不生效。
   这就是 `dist:*` 脚本都先跑 `build --prefix renderer` 的原因。
2. **`renderer/dist` 不存在时不会报错**，只会产出一个打开白屏的包。先确认 `renderer/dist/index.html` 存在。

## 4. 分平台命令与产物

### 4.1 macOS

```bash
cd desktop

# 当前机器架构（M 系列 = arm64）
npm run dist:mac

# 只要 Intel 包
npx electron-builder --mac --x64

# 一个包同时支持 Intel + Apple Silicon（体积约翻倍，推荐对外分发）
npx electron-builder --mac --universal

# 只要 dmg，不要 zip
npx electron-builder --mac dmg
```

| 产物 | 用途 |
|---|---|
| `MJCode-<v>-mac-<arch>.dmg` | 给人下载安装（拖进「应用程序」） |
| `MJCode-<v>-mac-<arch>.zip` | **自动更新用**（electron-updater 下载的是 zip，不要删） |
| `latest-mac.yml` | 自动更新元数据（含 sha512），发 Release 时必须一起上传 |

> `--universal` 需要同时下载 arm64/x64 两份 Electron，首次会慢；本项目运行时无原生模块（`npmRebuild: false`），不会出现双架构二进制冲突。

### 4.2 Windows

```bash
cd desktop

# 在 Windows 上（推荐）
npm run dist:win

# 在 macOS 上应急（需先装 wine）
npx electron-builder --win --x64
```

| 产物 | 说明 |
|---|---|
| `MJCode-<v>-win-x64.exe` | NSIS 安装包（可选择安装目录 / 创建桌面快捷方式） |
| `latest.yml` | Windows 自动更新元数据，随 Release 一起上传 |

> 只配了 `nsis` 一个 target。想要免安装绿色版，加 `"portable"`：`npx electron-builder --win portable`。

### 4.3 Linux

```bash
cd desktop

# 在 Linux 上
npm run dist:linux

# 在 mac 上用 Docker
docker run --rm -v "$PWD":/project -w /project electronuserland/builder:latest \
  npx electron-builder --linux
```

| 产物 | 说明 |
|---|---|
| `MJCode-<v>-linux-<arch>.AppImage` | 单文件可执行，`chmod +x` 后直接运行 |
| `latest-linux.yml` | 自动更新元数据 |

> 只配了 `AppImage`。需要 deb/rpm 时：`npx electron-builder --linux deb rpm`（deb 需 `fpm`，Docker 镜像内已具备）。

## 5. 产物位置与命名

- 输出目录：`desktop/release/`（`build.directories.output`）
- 命名模板：`MJCode-${version}-${os}-${arch}.${ext}`

| 变量 | 实际取值 |
|---|---|
| `${version}` | `desktop/package.json` 的 `version`（CI 会按 tag 覆盖） |
| `${os}` | `mac` / `win` / `linux` |
| `${arch}` | `arm64` / `x64`（universal 构建为 `universal`） |
| `${ext}` | `dmg` / `zip` / `exe` / `AppImage` |

同时生成的 `builder-effective-config.yaml` 是**本次实际生效的配置快照**，排查「为什么产物跟预期不一致」时先看它。

## 6. 随包资源（打漏了会功能性故障）

| 配置 | 内容 | 漏了会怎样 |
|---|---|---|
| `files` | `main/ agent-core/ shared/ shared-ipc/ renderer/dist/ package.json` | 缺 `renderer/dist` → 白屏；缺 `main` → 起不来 |
| `extraResources` | `../ecosystem` → 包内 `Resources/ecosystem` | 生态中心（数字员工/技能/连接器）目录为空 |
| `asarUnpack` | `node_modules/sql.js/dist/sql-wasm.wasm` | 打包版唯一数据库引擎加载失败（WASM 在 asar 里读不到） |
| `build.mac.icon` / `win.icon` / `linux.icon` | `renderer/src/assets/logo.png` | 用 Electron 默认图标 |
| `npmRebuild: false` | —— | 打包期不重编原生模块（运行时依赖全是纯 JS/WASM） |

> `extraResources` 的 `../ecosystem` 是**相对 `desktop/`** 的路径。若把 `desktop/` 单独拷出去打包，会因找不到该目录而静默缺少资源——请始终在完整仓库里构建。

## 7. 签名与公证（不签名也能装，但有代价）

| 平台 | 不签名的后果 | 解决 |
|---|---|---|
| macOS | Gatekeeper 提示「无法验证开发者」，双击被拦 | 系统设置 → 隐私与安全性 → 「仍要打开」；或命令行 `xattr -cr "/Applications/MJ Coder.app"` |
| Windows | SmartScreen 提示「未知发布者」 | 「更多信息」→「仍要运行」 |
| Linux | 无强制签名 | —— |

启用方式（**无需改工作流**，secrets 就位即自动签）：

| 平台 | Secrets |
|---|---|
| macOS 签名 | `CSC_LINK`（Developer ID Application .p12 的 base64）+ `CSC_KEY_PASSWORD` |
| macOS 公证 | `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID` |
| Windows 签名 | `CSC_LINK`（.pfx 的 base64）+ `CSC_KEY_PASSWORD` |

公证所需的 `hardenedRuntime` / `entitlements` / `notarize` 片段、证书申请流程、失败排查，见《签名公证更新演练Runbook.md》，本文不重复。

⚠️ **自动更新与签名强相关**：Windows 侧 `verifyUpdateCodeSignature: true`（默认）会校验更新包的发布者，未签名包的自动更新会被拒绝。内测阶段若必须自更新，需临时关闭该校验并在 Release 说明里标注。

> 本次修复记录：该字段原先被误写在 `build.mac` 下。`verifyUpdateCodeSignature` 只属于 Windows 配置，
> 放错位置会让 electron-builder 的 schema 校验直接失败（`unknown property`），**整个打包命令跑不起来**。
> 已移到 `build.win`。

## 8. 自动更新（若启用）

- 更新源：`build.publish` = GitHub Releases（`jasonma1210/MJCoder`，channel `latest`）
- 上传：`npx electron-builder --publish always`（本地需 `GH_TOKEN`）
- **必须一起上传**：安装包 + `latest*.yml` + `*.blockmap`。缺 yml 客户端不会提示更新；yml 里的 sha512 与实际文件不一致会导致下载后校验失败。
- 关闭自动发布：`--publish never`（CI 默认走仓库变量 `PUBLISH_RELEASE`）

## 9. 推荐：正式发版走 CI（唯一合规路径）

`.github/workflows/ci.yml` 里已有 `release` job：

- 触发：打 tag `v*`（如 `v0.1.0`）
- 前置：`verify` job 全绿（含 116 项测试、语法门禁）
- 矩阵：`macos-latest` / `windows-latest` / `ubuntu-latest`
- 每个 runner 只打**自己平台**的包（`npx electron-builder --publish <never|always>`）
- 产物：Actions Artifacts `MJCode-<os>-<通道>-<sha>`；若仓库变量 `PUBLISH_RELEASE=true` 则同时创建 GitHub Release
- 通道（`latest` / `beta`）由 tag 形态自动判定，见 §9.5

```bash
# 一次完整的合规发版
git tag v0.1.1 && git push origin v0.1.1
```

> ⚠️ **架构覆盖提醒**：当前 job 未指定 `--x64` / `--arm64`，产物架构取决于 runner 本身。
> 若 `macos-latest` 是 Apple Silicon runner，则只产出 arm64 包，**Intel Mac 装不了**。
> 需要覆盖 Intel 时，把 Package 步骤改成 `npx electron-builder --mac --universal`（或给 matrix 增加 arch 维度）。

## 9.5 发 beta 版本（灰度：让部分用户先升）

> 适用场景：想先放给一小批用户试，确认没问题再推给所有人。
> 关键点：**beta 是「另一条通道」**，不是「一个新版本号」。稳定版用户完全感知不到 beta 的存在。

### 通道由 tag 的形态决定（没有开关，看 tag 长什么样）

CI 的 `Sync version from tag` 步骤会调 `desktop/scripts/resolve-update-channel.mjs` 解析 tag，
结果决定产物叫 `latest.yml` 还是 `beta.yml`：

| tag 形态 | 通道 | GitHub Release 类型 | 产出 yml | 谁能收到 |
|---|---|---|---|---|
| `v0.1.0`（无 prerelease 段） | `latest` | 正式 Release | `latest.yml` / `latest-mac.yml` / `latest-linux.yml` | **所有用户** |
| `v0.1.0-rc.1` | `beta` | prerelease | `beta.yml` / `beta-mac.yml` / `beta-linux.yml` | **只有切到 beta 通道的用户** |
| `v0.2.0-beta.3` | `beta` | prerelease | 同上 | 同上 |
| `v0.2.0-alpha.1` | `beta` | prerelease | 同上 | 同上 |

注意三点：

1. **`rc` / `alpha` 都归到 `beta` 通道**（不是各开一条）。客户端只有一个
   `MJ_UPDATE_CHANNEL=beta` 开关，`rc` 通道的 yml 没人会去读，等于白产。
2. **tag 写错会直接中止发布，不会静默当稳定版发**。`v0.1.0` 少写了个 prerelease 段、
   写成 `latest`、`1.0`、`vfoo`，脚本一律非零退出。这是有意设计的（fail-closed）：
   把 beta 误推成稳定版**不可逆**（用户装上后得靠 `MJ_ALLOW_DOWNGRADE=1` 手动退），
   而「这次没发出去」重打 tag 就好。
3. **beta 构建不会覆盖 `latest.yml`**。electron-builder 在 GitHub provider 下只产出
   当前通道的 yml（`computeChannelNames` 短路），所以稳定版用户不会被 beta 波及。

### 发一个 beta

```bash
# 1. tag 里必须带 prerelease 段，通道才会是 beta
git tag v0.2.0-beta.3 && git push origin v0.2.0-beta.3

# 2. 等 CI release job 跑完（三平台），核对产物里出现 beta*.yml
#    Actions → 该次 run → Artifacts: MJCode-<os>-beta-<sha>
#    下载后应能看到 beta.yml（win）/ beta-mac.yml / beta-linux.yml
```

若仓库变量 `PUBLISH_RELEASE=true`，CI 会把它发成 GitHub **prerelease**。

### 客户端怎么拿到 beta

更新器读 `MJ_UPDATE_CHANNEL` 环境变量（默认 `latest`）：

```bash
# macOS / Linux
MJ_UPDATE_CHANNEL=beta open -a "MJ Coder"      # mac
MJ_UPDATE_CHANNEL=beta ./MJCode-*.AppImage     # linux
# Windows（PowerShell）
$env:MJ_UPDATE_CHANNEL="beta"; & "$env:LOCALAPPDATA\Programs\MJ Coder\MJ Coder.exe"
```

代码侧配套（`desktop/main/updater/index.js`）已经就位，**两件事必须同时成立**才有 beta：

- `autoUpdater.channel = 'beta'` —— 决定去拉 `beta*.yml`；
- `autoUpdater.allowPrerelease = true` —— GitHub provider 默认**只认正式 Release**，
  只设 channel 不设这个，beta 通道会永远显示「已是最新」（这是 X22 的原始故障）。

> 目前没有 UI 开关，只能靠环境变量。给最终用户批量灰度前，建议先补一个设置项
> （写进 `MJ_UPDATE_CHANNEL`，重启生效）。

### 从 beta 回到稳定版（回滚）

默认**不允许降级**（`allowDowngrade` 为 false），否则某个通道的旧 metadata 会把用户
静默回退到低版本。需要人工回滚时显式开：

```bash
MJ_ALLOW_DOWNGRADE=1 MJ_UPDATE_CHANNEL=latest open -a "MJ Coder"   # mac
```

含义：允许版本号变小 + 切回 latest 通道。装回稳定版后，下次正常启动**去掉这两个变量**，
否则会持续接受降级。

完整回滚流程（含撤 Release、重发旧 yml）见《发布回滚Runbook.md》。

### 常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| beta 用户一直「已是最新」 | 只设了 channel，没设 `allowPrerelease` | 确认 `MJ_UPDATE_CHANNEL=beta` 且代码里 `allowPrerelease=true` 仍在 |
| Release 里有 beta 包，但没 `beta.yml` | Package 步骤没传 `-c.publish.channel` | 看 CI 日志的「解析结果：channel=...」那行 |
| CI 在 `Sync version from tag` 就红 | tag 不是合法 semver（如 `v0.1`、`1.0`） | 重打合规 tag（`v0.1.0` / `v0.1.0-rc.1`）后重新 push |
| 稳定版用户收到了 beta | 误用了无 prerelease 段的 tag（`v0.2.0` 而不是 `v0.2.0-beta.3`） | 已发出的无法撤回，只能发更高版本号修复 |
| 打包报 `configuration.publish should be one of these` | 把 `generateUpdatesFilesForAllChannels` 写进了 `build.publish` | 它是 **build 顶级**字段，挪出去（GithubOptions 不接受额外属性） |

## 10. 安装说明（给最终用户）

### macOS
1. 下载 `MJCode-<v>-mac-<arch>.dmg`，双击打开
2. 把「MJ Coder」拖进「应用程序」
3. 首次启动：
   - 已签名/公证：直接双击
   - 未签名：右键 →「打开」→「打开」；若提示「已损坏」，执行
     `xattr -cr "/Applications/MJ Coder.app"` 后重试

### Windows
1. 下载 `MJCode-<v>-win-x64.exe`
2. 双击 → SmartScreen 提示「未知发布者」→「更多信息」→「仍要运行」
3. 默认装到 `%LOCALAPPDATA%\Programs\MJ Coder`（无需管理员权限）
4. 卸载：设置 → 应用 → MJ Coder

### Linux
```bash
chmod +x MJCode-<v>-linux-<arch>.AppImage
./MJCode-<v>-linux-<arch>.AppImage
```
若提示 FUSE 相关错误：`sudo apt install libfuse2`（Ubuntu 22.04+），
或临时用 `./MJCode-*.AppImage --appimage-extract-and-run`。

### 首次使用
首次启动会播放约 2.4 秒启动页（可点击跳过），随后进入 9 步引导：
配置模型 → 安全档 → 数字员工 → 技能 → 连接器 → 项目 → 首个任务 → 完成。
所有密钥仅存本机（safeStorage 加密），不上传服务器。

## 11. 版本号怎么改

```bash
cd desktop
npm version 0.2.0 --no-git-tag-version   # 只改 desktop/package.json
```

- 正式发版时三处 `package.json`（desktop / server / renderer）必须一致——规范见《发布回滚Runbook.md》
- CI 会用 tag 覆盖 desktop 的 version（`npm version "$VERSION"`），本地改了也会被覆盖
- 版本号会进入安装包文件名与 `latest*.yml`，**不要在已发布的版本号上重发**（自动更新会认不出新版本）

## 12. 排错表

| 现象 | 原因 | 解决 |
|---|---|---|
| `configuration.mac has an unknown property ...` | 配置字段放错层级（schema 校验失败） | 对照 `node_modules/app-lib/scheme.json` 查该字段属于哪个平台块 |
| 打出来的包打开是**白屏** | `renderer/dist` 为空或过期 | 先 `npm run build --prefix renderer` |
| 图标没生效 / 报 `image size must be at least 512x512` | 图标尺寸或格式不符 | 换 ≥512×512 PNG（mac 建议 1024，Windows 建议另做 .ico） |
| mac 上打包 Windows 报 wine 相关错误 | 未装 wine / wine 版本不匹配 | `brew install --cask wine-stable`；仍失败则改用 CI |
| Linux 包在 mac 上构建失败（appimage 工具链） | 跨平台不支持 | 用 `electronuserland/builder` Docker 镜像 |
| 打包后 `npm test` 出现 `ERR_DLOPEN_FAILED` | 历史坑：原生模块被重编成 Electron ABI | `npm rebuild better-sqlite3`（本项目 `npmRebuild:false` 已规避） |
| `Brokered file token refused` / 写 `release/` 被拒 | 运行环境的文件写保护（非项目问题） | 换普通终端执行，或把 `-c.directories.output` 指到可写目录 |
| 公证失败 `status: Invalid` | entitlements 或签名链问题 | 见《签名公证更新演练Runbook.md》第三节 |
| 自动更新提示「签名无效」 | 更新包未签名 / 发布者不匹配 | 签名，或内测期临时关 `verifyUpdateCodeSignature` |

## 13. 打包后自检清单

- [ ] `release/` 里能看到 `.dmg`（或 `.exe` / `.AppImage`）+ `latest*.yml`
- [ ] 双击安装包能完成安装，应用图标与名称正确
- [ ] 打开后**不是白屏**，启动页出现并进入引导（首次）
- [ ] 引导里生态中心的三类目录非空（说明 `extraResources/ecosystem` 打进去了）
- [ ] 新建会话发送一句话，能返回内容（说明模型凭证与数据库正常；打包版走 sql.js WASM）
- [ ] 打开「文件」面板能看到项目文件树（说明 `files` 白名单没漏东西）
- [ ] 关于/设置里显示版本号与 `package.json` 一致
