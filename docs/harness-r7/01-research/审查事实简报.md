## 5. 2025–2026 主流 Agent Harness 实践对齐

> 来源纪律：只采用 MCP 官方、OpenAI 官方、Anthropic 官方、Google ADK 官方文档/仓库；未采用二手博客。项目裁定仍锚定 `924909c` + 当前工作区，均为静态比对。

### 5.1 MCP 规范演进

1. **2025-06-18 是重要分水岭**：加入 structured tool output、elicitation、resource links、OAuth Resource Server/Resource Indicators，并要求 Streamable HTTP 后续请求带 `MCP-Protocol-Version`。  
   来源：<https://modelcontextprotocol.io/specification/2025-06-18/changelog>。  
   MJCode：工具分页、会话恢复、roots/completion/logging已做；版本头缺失（F-006），resources/prompts/structured output 未接（F-014）。
2. **2025-11-25**：OIDC discovery、增量 scope、URL mode elicitation、sampling tool calls、experimental tasks。  
   来源：<https://modelcontextprotocol.io/specification/2025-11-25/changelog>。  
   MJCode：协议字符串升到 2025-11-25，但上述新增能力大多“透传/不解释”或未实现。显式拒绝 sampling/elicitation在没有 HITL UI 时是安全选择。
3. **MCP 的核心 surface 不只有 tools**：server 可提供 resources/prompts/tools，client 可提供 roots/sampling/elicitation；各能力通过 capability negotiation 渐进启用。  
   来源：<https://modelcontextprotocol.io/specification/2025-11-25/>。  
   MJCode：实质是 tools profile；需在文档中准确命名。
4. **动态 server 管理与 progressive discovery 成为官方 client best practice**：保持最小常驻 server、按需连接、缓存定义、监听 list_changed；同时提醒“每回合增删 tool schema 会破坏 prompt cache”。  
   来源：<https://modelcontextprotocol.io/docs/2025-06-18/develop/clients/client-best-practices>。  
   MJCode：默认 tier 懒启动、意图预热、工具缓存、list_changed、稳定排序均对齐；当前 dirty diff 改为只把已连接工具给 renderer，方向正确，但需补 conversation 内稳定策略。
5. **2026-07-28 方向已转向 stateless + per-request metadata + extensions**，experimental tasks 移到扩展，MRTR 替换 server-initiated requests，并强调 tools/list 确定性排序与 OpenTelemetry trace context。  
   来源：<https://modelcontextprotocol.io/specification/2026-07-28/changelog>。  
   MJCode：仍是 handshake/session era 客户端；短期兼容没问题，长期需决策双栈还是冻结 2025-11。

### 5.2 Agent loop 与上下文工程

1. Anthropic 将主流上下文策略归纳为：tool result clearing、compaction、结构化 notes/memory、subagent 隔离；核心是“最小高信号 token 集”。  
   来源：<https://anthropic.com/engineering/effective-context-engineering-for-ai-agents>。  
   MJCode：工具长输出 8k 摘要/落盘、15k 截断、70/80% compaction、图片占位符、SQLite memory 均对齐。
2. Claude 平台的 context editing 会清除 stale tool calls/results；memory 在客户端存储，context editing + memory 的内部评测相较 baseline 提升 39%，100-turn search token 降 84%（厂商内部评测，非独立复现）。  
   来源：<https://anthropic.com/news/context-management>。  
   MJCode：已有工具结果摘要与记忆；尚无按“陈旧程度”清理已保留短结果的独立策略，主要依赖整体 compaction。
3. 大工具库的主流做法是 tool search/deferred loading，而不是把全部定义塞进上下文；Anthropic 官方示例强调 defer-loading 与 programmatic tool calling。  
   来源：<https://anthropic.com/engineering/advanced-tool-use>。  
   MJCode：server 级意图预热已降低暴露面，但粒度仍以 server 为主，未到单工具搜索索引；`code_exec` 已具备 programmatic 路线基础。
4. KV-cache 友好要求稳定前缀、少重写、稳定 tool 顺序。  
   来源：MCP client best practices（上文）及 Claude Code prompt cache说明 <https://docs.anthropic.com/en/docs/claude-code/costs>。  
   MJCode：`MAX_REWRITES_PER_RUN=5`、prefix section、MCP稳定排序对齐；按意图增删 tools 仍会造成预期 cache rebuild，应记录为成本而非功能错误。

### 5.3 多智能体 / subagent

1. Anthropic Agent SDK 明确：subagent 使用独立 context window，仅把相关结论返回 orchestrator；用途是并行化与上下文隔离。  
   来源：<https://anthropic.com/engineering/building-agents-with-the-claude-agent-sdk>。  
   MJCode：`spawn_subagent` 新 runAgent、只读工具集、父上下文 last 6 条/每条 800 字、结果回父，方向对齐。
2. 长任务仅 compaction 不够；结构化 handoff artifact、context reset、planner/generator/evaluator 分离是 2025–2026 的演进方向。  
   来源：<https://anthropic.com/engineering/effective-harnesses-for-long-running-agents>、<https://anthropic.com/engineering/harness-design-long-running-apps>。  
   MJCode：有 checkpoint、task DAG、聚合器、独立 V-L3；但 orchestrator 的 evaluator 与 generator 是否真正模型隔离需 P3 行为验证。
3. Google ADK 建议从单 agent 渐进到 graph/multi-agent workflow，将确定性代码与非确定性推理解耦。  
   来源：<https://google.github.io/adk-docs/agents/>。  
   MJCode：DAG 校验、拓扑分层、WorkerPool、重规划符合该方向。

### 5.4 沙箱与权限

1. OpenAI Codex 默认 workspace-write、网络关闭；sandbox 负责技术边界，approval 负责越界时机，两者正交。macOS 用 Seatbelt，Linux 主流用 Landlock+seccomp，bubblewrap也是官方工程文档认可的隔离工具之一。  
   来源：<https://openai.com/index/building-codex-windows-sandbox/>、<https://openai.com/index/running-codex-safely/>、官方仓库迁移记录 <https://github.com/openai/codex/commit/ab753387ccf54aba94ab8c54da3149c743dbe189>。  
   MJCode：Seatbelt/bwrap/Windows 分档 + approval 独立矩阵总体主流；Linux 与 Codex 的 Landlock+seccomp 有实现差异，不直接判缺陷。
2. 主流审批粒度是“沙箱边界/外部副作用/未知域名”而非所有动作一律询问；可做 session scope allow，但高风险透明。  
   来源：OpenAI 内部安全部署文档（上文）。  
   MJCode：L1不可豁免、L2/L3规则记忆、外部动作无人值守 guard 对齐；F-002 表明登记门禁还没有把这套安全约束机器化守牢。

### 5.5 Eval 与 trace

1. OpenAI Agents SDK 把 handoff、guardrails、tracing/observability 当一等原语。  
   来源：<https://openai.com/blog/new-tools-for-building-agents>。  
   MJCode：trace JSONL、V-L1/V-L3、governance stats 已有；缺少统一 span/graph 查询面。
2. OpenAI eval best practice 是 eval-driven development、任务特定数据集、日志挖掘、自动评分与持续评估；反对只靠“感觉有效”。  
   来源：<https://platform.openai.com/docs/guides/evaluation-best-practices>。  
   MJCode：eval runner设计方向正确，但 CI 只跑 `--check`，实际 CE 未闭合（F-008）。
3. Google ADK/BigQuery Agent Analytics 用事件图、tool provenance、HITL、checkpoint、compaction、long-running tool 事件与 OpenTelemetry trace 来支撑离线评估。  
   来源：<https://google.github.io/adk-docs/integrations/bigquery-agent-analytics/>、<https://google.github.io/adk-docs/integrations/weave/>。  
   MJCode：本地优先不必上 BigQuery，但应考虑内部统一 trace schema + OTLP 可选导出，而不是只依赖 JSONL/console。

### 5.6 对齐总裁定

| 维度 | MJCode 当前状态 | 主流对齐度 | 主要差距 |

## 6. 需要用户裁决的决策点（供 P1 架构师）

### D-01 MCP 版本路线

- **问题**：冻结 2025-11 handshake，还是做 2026 stateless 双栈？
- **方案 A**：仅补齐 2025-11 合规（version header、resources/prompts可选）。成本低，短期兼容最好；未来还要迁移。
- **方案 B**：2025-11 + 2026-07 双栈。成本高（discover、per-request meta、MRTR、extensions、transport 重构），兼容面最大。
- **方案 C**：直接转 2026，放弃老 server。实现最干净，但会破坏大量现有连接器。
- **主流做法**：双 era 兼容/能力协商；建议先 A，预留 B 的 transport abstraction。

### D-02 MCP 产品 surface

- **问题**：继续定位 tools-only，还是补 resources/prompts/tasks/elicitation？
- **方案 A**：正式声明“tools profile”，sampling/elicitation继续拒绝。成本最低、风险可控。
- **方案 B**：先补 resources/prompts（只读能力），保留 sampling/elicitation拒绝。中等成本、收益高。
- **方案 C**：全量实现 tasks + elicitation + sampling。成本/安全/UX最高，需要逐次同意与长任务状态机。
- **主流做法**：渐进 capability；建议 B。

### D-03 工具发现粒度与 prompt cache

- **问题**：server 级意图预热，还是单工具 search/defer？
- **方案 A**：保持 server 级，修好名称/描述安全。简单，但大 server 工具表仍重。
- **方案 B**：增加稳定 `search_tools/call_tool` meta-tool，定义宿主侧索引。上下文最低、实现/调试复杂。
- **方案 C**：混合：核心 native 常驻，MCP server 懒连，单工具按需展开。复杂度中等。
- **主流做法**：progressive discovery + stable cache breakpoint；建议 C。

### D-04 `supportsToolCall` 的真实语义

- **问题**：开关是展示元数据，还是执行硬门？
- **方案 A**：删除开关，避免虚假控制。成本最低。
- **方案 B**：false 时 `allTools=[]`，并切换无工具 system prompt。语义清晰，需处理任务依赖工具时的提示。
- **方案 C**：自动探测 provider 能力并允许用户覆盖。体验最佳，维护能力目录有成本。
- **主流做法**：capability gate 必须约束请求；建议 C，至少先 B。

### D-05 数字员工是否成为可执行 runtime

- **问题**：保持“模板库”，还是接入主对话角色选择？
- **方案 A**：保留库，删/隐藏 employeeRuntime 半成品并修文档。成本低。
- **方案 B**：线程级选择员工，启动 run 前取 rolePreset，UI 明示 tools/approval/sandbox。中成本。
- **方案 C**：多员工编排/DAG。成本高，需要主体 RBAC、身份 trace、最小权限继承。
- **主流做法**：先单 runtime preset，再扩多 agent；建议 B。

### D-06 工具登记安全门禁

- **问题**：沿用源码扫描矩阵，还是建立声明式 registry？
- **方案 A**：补测试读取 approval.js/REVERSIBILITY/timeouts，继续多处登记。改动小、仍有漂移面。
- **方案 B**：单一 `toolRegistry` 同时生成 schema、handler name、timeout、approval、reversibility、label。改造大，长期最可靠。
- **方案 C**：分两步：先 A 止血，再 B 收敛。
- **主流做法**：声明式 policy/registry + 生成式校验；建议 C。

### D-07 Eval 执行频率与成本

- **问题**：何时真正跑 10+5 个 Agent eval？
- **方案 A**：只保留 `--check`。零模型成本，但不能测能力回归。
- **方案 B**：PR 跑 2–3 个小样，nightly/发布前跑全量；结果做基线差分。成本可控。
- **方案 C**：每次提交全量。反馈最及时，费用/非确定性/时长最高。
- **主流做法**：持续评估 + 分层任务集；建议 B，并固定模型 snapshot/重复次数/置信区间。

### D-08 Trace 标准化

- **问题**：继续本地 JSONL，还是引入 OpenTelemetry-compatible spans？
- **方案 A**：JSONL 不变，只补 schema version/run graph。低成本。
- **方案 B**：内部 span model + 可选 OTLP exporter（默认本地、不上传）。中成本，可观测性最好。
- **方案 C**：接云分析平台。与 local-first 定位冲突、隐私成本高。
- **主流做法**：OTel-compatible，export 可选；建议 B。

### D-09 Linux sandbox 后端

- **问题**：维持 bwrap，还是增加 Landlock+seccomp/容器？
- **方案 A**：bwrap 继续，强化可用性探测和失败说明。兼容性高。
- **方案 B**：Landlock+seccomp 主后端，bwrap fallback。安全对标高，Rust/native 成本高。
- **方案 C**：容器后端 opt-in。隔离强，启动慢、环境桥接复杂。
- **主流做法**：OS-enforced + network default-off + approval 正交；建议 A 近期、B 中期。

### D-10 文档发布纪律

- **问题**：技术流程文档是否纳入 Git？
- **方案 A**：纳入 `docs/` 并在头部写 commit、生成时间、计数脚本。最可复核。
- **方案 B**：保持本地生成，但每次输出带内容 hash 和 `git show` 可重建脚本。仍有丢失风险。
- **方案 C**：仅保留代码内生成式架构清单，不维护长文档。减少漂移，降低人类可读性。
- **主流做法**：docs-as-code + CI 校验；建议 A。
