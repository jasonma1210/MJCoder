#### 3. 接口 / 数据模型

**3.1 新增 era 判定（`mcpProtocol.js`）**

```js
// 协议时代：握手时代（<=2025-11-25）与 stateless 时代（>=2026-07-28）
export const ERA_HANDSHAKE = 'handshake';
export const ERA_STATELESS = 'stateless';

/** @returns {'handshake'|'stateless'|'unsupported'} */
function eraOf(version) {
  if (typeof version !== 'string') return 'unsupported';
  // stateless era 的版本号按日期序比较，不写死单值：2026-07 之后的补丁版必须也能进
  if (version >= '2026-07-28') return ERA_STATELESS;
  if (SUPPORTED_PROTOCOL_VERSIONS.includes(version)) return ERA_HANDSHAKE;
  return 'unsupported';
}
export const STATELESS_MIN_VERSION = '2026-07-28';
export const PROTOCOL_ERA = Object.freeze({
  HANDSHAKE: ERA_HANDSHAKE,
  STATELESS: ERA_STATELESS,
  STATELESS_MIN_VERSION,
  eraOf,
});
```

> 设计取舍：用**字符串日期比较**而非 `SUPPORTED_PROTOCOL_VERSIONS` 白名单来判 stateless。理由：stateless era 的版本是日期序，白名单会让「服务端升了个补丁版」直接变 `unsupported` 并触发断开，与规范「客户端 SHOULD 断开不兼容版本」冲突（它本来就兼容）。白名单只保留给握手时代（那四个版本差异是**真实差异**，比如 icons/tasks）。

#### 7. 不可逆点

**P3（默认开启）不可逆。** 一旦默认 defer，模型的「工具可见性」从确定性变成上下文相关 —— 同一句用户请求在不同历史下可能看到不同的工具集。这会让**所有既有排障经验失效**（「模型为什么不用 xx 工具」的答案从「没这个工具」变成「这一轮它被 defer 了而且模型没想到去搜」）。

为什么难回退：回退后需要重新验证「模型在没有 defer 时的行为」是否还正常，而这项工作没有任何人愿意做第二次。

#### 8. 风险 + 回滚方案

| 风险 | 概率 | 影响 | 回滚 |
|---|---|---|---|
| 模型不去调 `search_tools`，直接说「我没有这个能力」 | **高** | 功能可用性感知为负 | 在 `BASE_PROMPT` 里加一条硬承诺（`tool-registration-matrix` 的 ⑥ 断言要求「承诺的工具必须真实存在」，`search_tools` 真实存在，可通过）；P1 影子期用 eval 成功率做闸 |
| defer 导致前缀缓存全失效（每次 run 的工具表不同） | 中 | 成本上升，抵消收益 | 索引文本按**固定顺序**（内置在前后按名排序）渲染；`deferred` 集合的选取必须确定性（按 schemaBytes 降序、同名序兜底） |
| 与 `MAX_MCP_TOOL_CALLS_PER_SERVER=40` 交互：defer 后调用计数语义变化 | 低 | 熔断提前触发 | 计数点在**实际调用**处（不变），defer 不改变调用次数 |
| `agent-core/index.js` 已 3591 行（`[H]`），改动会加剧 God File | 高 | `max-lines` 门禁与可维护性 | 决策函数与索引全放 `shared/toolIndex.mjs`；`index.js` 只加 ≤ 30 行的调用点。**禁止**为此在 `BASELINE_800` 加条目（那清单只减不增） |

#### 9. 为什么不能本批直接落地

**缺数据。** `warnRatio=0.6` 这类阈值必须用真实工具表分布定，而分布采样（`toolTableBytes`）**刚落地还没攒够样本**（`[W]` 未提交）。现在定阈值等于拍脑袋，而错误的阈值有双向代价：太低 → 小工具集也被 defer（不必要的复杂度）；太高 → 撞线后才切（那一次请求已经超限，切了也救不回来）。

**可以本批做的部分**：P0（索引模块 + 检索 + 确定性渲染 + 套件），估 2–3 天；再接 P1 影子模式（也是零行为变化）。

```js
 * @property {string[]} writeDeniedPaths                                    受保护路径（.git/hooks、~/.ssh…）
 * @property {string[]} unixSockets                                         允许连接的 unix socket 路径
 * @property {boolean} network                                              是否放行 TCP
 */
export function buildLandlockRuleset(policy, cwd, protectedPaths)  // → LandlockRuleset
```

映射纪律（三级 sandbox policy → 规则）：

| policy | cwd 写 | 系统读 | network | 依据 |
|---|---|---|---|---|
| `read-only` | ❌ | ✅ | ❌ | 与 `buildBwrapArgv` 现有 `--ro-bind` 语义对齐 |
| `workspace-write` | ✅（cwd 内） | ✅ | ❌ | 对齐现有 bwrap 默认（网络关闭） |
| `full-access` | 不走 OS 沙箱 | — | — | `osSandboxUsable` 已在 `sandbox.js:225` 直接返回 `use:false` |

**3.3 seccomp 过滤器**

`[未验证]`：`sandboxLinux.js:342-348` 明确记录 seccomp 需要 **fd 传递 + spawn 路径**，当前 bwrap 走的是 argv 拼接，因此 seccomp 至今没接。Landlock 路线的正确做法是：
- 在 `spawn` 的 `preExecFn`（Node `child_process.spawn` 的 `options.detached` 之外，Linux 需 `posix_spawn` 钩子或先 `exec` 一个小 wrapper）里 install filter；
- Node 标准库**没有** pre-exec 钩子 → 必须 native 模块（N-API）或「起一个固定小二进制做 wrapper」。
- **这一点我无法在本环境验证可行性细节，标 `[未验证]`，实现前必须先做 1 天 spike。**

#### 5.1 为什么不做「模块加载期自预热」（已评估并否决）

> **状态：已否决（2026-10-20，主理人裁决）并已删除（实测 `grep -rn NO_WARM` → 0 处，`setImmediate` 自调度无残留，`sandbox.js` 由 325 行回到 306 行）。** 否决前曾实现过一版：`sandbox.js` 模块末尾 `setImmediate(warmSandboxProbe())` + `MJCODE_SANDBOX_NO_WARM` 逃生阀。
> **否决策略本身就是资产** —— 与 `roleClamp.mjs` 的「物理单文件已被否决」同样处理：写清理由，防止下一轮重新发明。

四条否决理由（按权重排序）：

| # | 理由 | 展开 |
|---|---|---|
| 1 | **给全仓测试强加了一条隐性前置条件** | 连实现者本人都得写「统计 spawn 的验收脚本要先 `await new Promise(r=>setImmediate(r))` 排空，否则假红」。这意味着从此每个写 spawn 计数断言的人，**若不知道这条规矩就会拿到假红，并去修一个不存在的 bug**。这类「污染他人断言」的副作用，成本不由引入者承担，因此最容易扩散 |
| 2 | **收益不成立** | 预热只把一次探测从「第一次 exec」挪到「进程启动后下一个 tick」，**探测次数一次没少**；而 TTL 缓存（`PROBE_TTL_DEFAULT_MS = 60000`）已保证稳态零成本。用「改变全局副作用时序」换「几百毫秒的位移」，不划算 |
| 3 | **它消掉了 #11 原有的一个优点** | 原设计要求「**模块加载期零探测**」。`sandbox.js` 被 `tools/exec.js` 普遍引入（`main.js:520` → `exec.js` → `sandbox.js`），**import 一个纯判定模块不应产生 spawn 副作用** |
| 4 | **它引入第 3 个环境变量** | `MJCODE_SANDBOX_NO_WARM`（另两个是 `PROBE_TTL_MS` 与 `BWRAP_BIN`）。逃生阀越多，「某套件设了某一扇、行为与生产不一致」的概率越高 |

**最终形态（已落地）**：自调度与 `NO_WARM` 已删除；`warmSandboxProbe()` **保留导出**，注释写明「**宿主可选调用；不调用时首次探测由 TTL 缓存承担；刻意不做模块加载期自预热**」。先例是 `resetSeatbeltProbe` —— 同样生产零调用、同样**不是**死代码（它是可选 API）。

**替代它的正向守卫（比预热那套更值得保留）**：**`require` 两个模块后 bwrap spawn 必须 = 0，且同步读就对、不需要任何排空/等待**。这条把「模块加载期零副作用」这个**原本只是口头约定**的性质变成了可执行断言 —— 而预热那套做的恰恰相反：它把这条性质破坏掉，然后再要求每个下游测试自己去排空。**判据写法见 §5 的 1c。**

**唯一保留的事实（若仍要评估此路）**：`PROBE_TIMEOUT_MS = 10000`（`sandboxLinux.js`）意味着 bwrap 卡死时探测会占住 10s —— 无论同步探还是预热，这个上界都存在，区别只是**在前台还是挪后**。

#### 7. 不可逆点

**P4（默认切 Landlock）不可逆。** 一旦默认切换：
- 所有 Linux 用户走一条**新的 syscall 限制面**，任何漏掉的规则（例如漏了 `/dev/null` 写、漏了某个 TLS 证书路径）会让**正常命令莫名 EACCES**；
- 这类失败的形态是「工具报错但原因不明」，与今天的 bwrap 失败（"bwrap 未安装"有明确 `reason`）相比**可诊断性更差**；
- 用户无法自己判断「是不是沙箱干的」。

为什么难回退：回退后需要重新验证「在 bwrap 下这些命令正常」——而 bwrap 路径在切换期间没人跑过，等于第二个未验证面。

**3.0b-1 剩余边界 E · `exec.js` 的 2 处「登记式 allow-list」（不是缺陷，但「数据单源」必须声明范围）**

新增断言 **2d「派生表达式棘轮（窄模式）」** 揭示了一个必须写清的事实：扫描范围是 **`approvalPolicy` / `main` / `workerPool` 必须 0 处手抄**，而 **`exec.js` 恰好 2 处**（`exec.js:155` `args.cwd ? 'workspace-write' : 'read-only'`、`:348` `rest.cwd ? ...`）—— 这 2 处是**登记在 allow-list 里的**，不是遗漏。

为什么保留：它们与 `hostPolicySnapshot` **角色不同** —— 那两处是「**本次执行的默认档**」回落，而 `hostPolicySnapshot` 是「**建组时固化、随组持久化**的快照」。`approvalPolicy.js` 的 JSDoc 里有一段「**边界说明（别过度声称）**」正是在讲这件事。

**而且它还有一层更硬的原因（`DERIVE_ALLOWLIST` 的注释里记着，容易被漏读）**：`exec.js` 实测 **799 raw / `split('\n').length` = 800**，**800 软档余 0 行** —— 改它至少要加一行 `require`，一加就撞 `max-lines` 800 软档，而纪律**禁止往 `BASELINE_800` 新增条目**。所以正确做法是「**先抽模块再改**」，属下一批（台账 `D-13-b`）。

> **⇒ 这解释了为什么 2 处会「合法留存」**：不是懒，是**行数预算死锁** —— 想收敛它，先得把它拆薄，而拆薄是独立工作。**没有这条说明，「allow-list 2 处」会被读成「没做完」。**

**2d 的两个设计细节（都值得照抄）**：

| 细节 | 做法 | 为什么 |
|---|---|---|
| **恰好相等棘轮** | `exec.js: 2` 是**恰好 2**，降到 1 也红 | 否则 allow-list 会**慢慢腐烂成永久豁免**（1 → 0 的中间态没人管，久了就成 3、4）。降 1 就红，等于强制把表收紧 |
| **code 口径（剥注释）** | 用 `readCode(rel)` 先剥注释再计次 | 注释里贴旧代码做提醒**不算违规**；否则「文档化」和「违规」互相排斥 |

> **⚠ 已知自匹配隐患（b3-clamp 上报，本文核实）**：`test/role-clamp-parity.test.mjs` **自身含 2 处**完整模式（断言标题 `:340` 与失败提示），因为解释判据时要引用那串字。**当前安全，纯粹因为 `DERIVE_ALLOWLIST` 硬编码 4 个 `main/` 文件、从不扫 `test/`**。
> **危险动作**：谁想「顺手扫一下 test/，防止测试里也冻结实现表达式」→ **门禁匹配到自己** → 计数恒 ≥2 永久红，而人会以为是代码退化。
> **防法（推荐①+③）**：① 把扫描面写死为「生产代码目录」，并在 2d 注释里注明「不要把 test/ 加进来，本门禁文案自带该模式」；③ 升成通用纪律 —— **凡按模式计次的判据，先回答「我自己的源码/文案会不会被这个模式命中」**（已写入 §0.2 第 8 条）。②「把匹配串拆开拼接让门禁自身不含完整模式」能免疫但可读性差，不推荐。

> **⇒ 所以「数据单源」的正确表述是**：「`cwd → 沙箱档` 的**快照路径**已单点（`sandboxTierForCwd`）；`exec.js` 的**逐次执行默认档**是另一条路径，仍有 2 处登记式回落。**写「全仓 0 处」是错的**，会被 2d 的 allow-list 打脸；写「快照路径 0 处手抄 + `exec.js` 2 处已登记」才对。

> **方法论（A′ 给出的教训，比缺口本身更值钱）**
> 「**某个值只有一处**」这类**全称命题，不能靠读一个文件得出** —— 必须按目标特征**全仓扫一次**。
> 本项第一版只看了 `approvalPolicy.js`，就宣布「唯一来源已收敛」，漏掉了 `main.js:1133` 的第二份手抄，**而所有门禁全绿**。这正是本项目「『不存在』也是全称命题」那条纪律的又一次实证：证明「有」只需一个样本，证明「只有一处」必须覆盖全集。
> **操作化**：凡在文档里写「唯一 / 只有一处 / 已全部收敛」，同批附一条可执行的**全仓扫描命令**（如 `grep -rn "workspace-write" desktop/main desktop/agent-core desktop/shared` 并逐个判定），并把该命令做成门禁。**没有扫描命令的全称命题，一律视为未验证。**

## §2 依赖图与推荐排期

### 2.1 依赖对验证一：D-02-B 是否**必须**在 D-03-C 之后？

**结论：不成立。这是一条假依赖。**

既有文档 `02-design/架构调整实现方案.md:445` 的推理是：「D-03（减少常驻工具）与 D-02（增加 resources/prompts）对上下文预算的作用相反 → 先收暴露面，再扩来源 → D-02-B 必须排在 D-03 之后」。

这个推理有两个漏洞：

1. **量纲不同。** `MAX_TOOL_SCHEMA_TOTAL_BYTES`（`contextBudget.mjs:84`）度量的是**一次模型请求里 `tools` 字段的体积**（同文件 `:81` 注释原话）。resources 内容进的是**消息正文**，走的是上下文窗口预算。两者不共享同一个计量器，因此「一增一减」并没有在同一本账上对冲。
2. **resources 可以是零常驻的。** 只要遵守「按需拉取 + 长度闸 + 不常驻 system」，「补 surface」的净上下文支出可以是 0 —— 此时它连「扩来源」都算不上。

**条件式（这是给产品的判据）**：

| 若产品要的形态是 | 依赖关系 | 理由 |
|---|---|---|
| 资源只在用户点开时预览、点「注入」才进上下文（推荐） | **无依赖，可并行** | 零常驻，不吃工具表预算 |
| 资源清单**常驻**在 system prompt 让模型自己选 | **D-03-C 必须先做** | 常驻 = 第二支固定支出，必须先有 headroom |
| resources 与 prompts 都要常驻模板 | **D-03-C 必须先做** | 同上，且量更大 |

**真实的前置是另一件事**：D-02-B 需要**资源专用的字节闸**（`MAX_RESOURCE_READ_BYTES` / `MAX_RESOURCE_INJECT_BYTES_PER_RUN`），而不是「工具表闸升强制」。见 C-6 与 D-02-B §3.3。

### 拍板项 A · D-07 的 eval 成本上限与授权

**背景**：`run-eval.mjs:48-49` 硬性要求 endpoint/model/key；真跑消耗用户自己的额度。没有授权 → D-07 只能停在 P0（纯离线差分脚本）。

| 选项 | 内容 | 成本量级 | 优点 | 缺点 |
|---|---|---|---|---|
| **A1** | 只授权 `tasks.json`（10 个）nightly，`tasks-hard.json`（5 个）只在发布前手动跑 | 10 任务 × 1 次/夜 | 覆盖主路径回归；成本可控 | hard 档的劣化发现晚 |
| **A2** | 全部 15 个 nightly | 15 任务 × 1 次/夜 | 覆盖完整 | 成本 ×1.5；hard 档波动大易假红 |
| **A3** | 不授权真跑，D-07 只交付 P0（离线差分 + 空基线） | 0 | 零成本 | 差分**永远没有基线可比**，等于 D-07 没做 |

**推荐 A1**。理由：`tasks-hard.json` 的 5 个任务本身就是高波动样本（名字就叫 hard），拿它做 nightly 阈值门禁会制造大量假红，从而**摧毁团队对差分的信任**——而信任一旦没了，后面所有门禁都会被 bypass。发布前手动跑能保留它的价值（发布决策需要最严的信号）又不用承担每日噪声。

**不决策的后果**：D-07 停在 P0。表面上「有差分脚本」，实际上 `baseline.json` 永远为空，`compare-baseline` 每次都走 exit 2。这是最坏的一种「假绿」：**门禁存在、看起来在守、但其实什么都没守** —— 与 `run-all.mjs:45-46` 记录的事故（`npm run eval` 存在却无人触发）完全同形。

> **✅ 主理人已裁决，2026-10-20：采纳 A1。**
> 授权范围：nightly + 发布前两档；任务集用 `tasks.json` 的 **10 个标准任务**；key 用**用户自有**；PR 级**不跑**真 eval（CI 保持零成本，只跑已在位的 `--check`）。
> 主理人理由：`--check` 已经在跑（零成本），真跑的增量价值集中在「发版前是否退化」；PR 级跑全量会烧用户 key 且非确定性高，收益不抵成本。
> **对施工的直接影响**：D-07 的 P1（本地采基线）与 P2（nightly workflow）**已解锁**，可进 B3-β；P3（差分接红）仍需 ≥5 次基线跑校准阈值后才可开。`tasks-hard.json` 不进 nightly，只在 `workflow_dispatch` 的发布前档手动跑。
