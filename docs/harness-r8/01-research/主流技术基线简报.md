## §0 一句话结论

**2026 年的事实标准（已收敛，可放心对齐）**：

1. **协议分层已定局、不是二选一**：MCP 管「agent ↔ 工具/数据」（纵向），A2A 管「agent ↔ agent」（横向）；两者在 2026-08 归入同一个中立基金会（Agentic AI Foundation, AAIF）下属，**互补而非收敛**；IBM 的 ACP 已并入 A2A，**不应再作为新项目的架构选择**。
2. **MCP 当前规范版本是 `2026-07-28`**，且这是一次**断裂式升级**：协议级 session 与 initialize 握手被移除，改为无状态请求/响应；新增 `server/discover`、`Mcp-Method`/`Mcp-Name` 头路由、MRTR（多轮往返请求）、可缓存 list 结果、正式扩展框架与 12 个月弃用窗口。
3. **SKILL.md 已成为能力分发的跨平台事实格式**，并被更进一步打包为 **Agent Plugins 1.0.0（2026-08-06）**（`plugin.json` + `skills/` + `mcp.json`）。但同时：**技能市场的安全扫描结论普遍在 26%–37% 有缺陷**，即"可分发"与"可信任"是两件事。
4. **上下文工程的主流配方已经固定**：先 offload（工具输出落盘）再 summarize（压缩历史）+ prefix cache 复用 + 工具定义延迟加载（deferred loading / tool search）+ 子代理上下文隔离 + JIT 检索 + 结构化记忆文件。Anthropic 已把 compaction 做成**服务端能力**（`compact-2026-09-04`），不是各 harness 自己写 summarizer。
5. **多智能体的收敛结论是明确的**：**单一主循环拥有完整上下文 + 派生一次性隔离子代理只回传压缩摘要**，胜过多角色自由编排（peer GroupChat / swarm）。token 开销是硬约束（Anthropic 自述多智能体约 15× 于 chat）。
6. **持久化上"事件日志 + 可恢复"是必备项**，但**机制分成两派且尚未统一**：状态快照（LangGraph checkpointer）vs 持久执行重放（Temporal / DBOS / Restate）。共同铁律只有一条：**绝不重放非确定性步骤（LLM 调用必须成为被记录的 Activity）**。
7. **fail-closed 已是事实标准表述**，且在多家官方实现中落到具体开关（如 sandbox 不可用时直接失败、工具定义变更即拒绝）。

**仍在分化、必须点名的 5 处（不可假装已有标准）**：

| # | 分化点 | 具体分歧 |
|---|---|---|
| D1 | **OTel GenAI 语义约定是否稳定** | 一手仓库（open-telemetry/semantic-conventions-genai）全部标记 `Development`、截至 2026-10-12 **零 tagged release**；但多家厂商博客宣称"2026-06 已稳定"。**以一手为准：未稳定。** |
| D2 | **持久化的机制选型** | 快照派（LangGraph）vs 重放派（Temporal/DBOS/Restate）。两派失败方向相反，业界没有统一答案，只有统一铁律。 |
| D3 | **多智能体编排的命名与层级** | supervisor / hierarchical / orchestrator-worker / swarm 各家叫法不同（LangGraph=supervisor，CrewAI=hierarchical，AutoGen=group chat with manager，OpenAI=orchestrator-worker），**是同一族形状的不同 ergonomics**，没有权威命名。 |
| D4 | **技能/插件的信任模型** | Agent Plugins 1.0.0 明确不定义安装、分发、权限、沙箱、来源验证；各客户端自定。**标准只统一了"包"，没统一"信任"。** |
| D5 | **记忆的工业实现选型** | Mem0（抽取式双存储）/ Zep-Graphiti（时序知识图）/ Letta（LLM 自管理分页）三条路线并存，各有适用场景，无胜者。 |

### 主线 1 · 协议层：MCP 与 A2A / ACP

#### 结论

- **MCP 当前规范版本 = `2026-07-28`**（【一手】modelcontextprotocol.io 版本页明确："The current protocol version is 2026-07-28"）。上一代是 `2025-11-25`。
- **MCP 已捐入 Linux Foundation 旗下 Agentic AI Foundation（AAIF）**（【一手·旁证】MCP 官方博客页脚版权声明 "Model Context Protocol a Series of LF Projects, LLC"；成立与成员名单见【二手】多家一致转述为 2025-12，创始成员含 OpenAI / Anthropic / Google / Microsoft / AWS / Block）。
- **A2A 现状**：Google 2025-04 发布 → 2025-06 捐入 Linux Foundation → **2026-08-17 成为 AAIF 托管项目**（Growth Stage），与 MCP 同处一个中立基金会。【二手，日期口径见 §3-6】
- **ACP 结局**：IBM 的 Agent Communication Protocol 已**并入 A2A**，ACP 开发收尾，其负责人进入 A2A TSC；BeeAI 用户经 `A2AServer` 适配器迁移。**新项目不应再选 ACP。**
- **二者关系：并存且互补，不收敛**。【一手·AAIF/LF 立场转述】MCP = "how an agent connects to tools and data sources"；A2A = "how agents communicate and coordinate across organizational boundaries"。

#### 主流做法

**MCP 2026-07-28 的关键变化（【一手】官方 release post + 版本页）**：

| 变化 | 内容 | SEP 编号 |
|---|---|---|
| 无状态协议核心 | 移除 `initialize`/`initialized` 握手与 `Mcp-Session-Id`；每个请求自描述，携带协议版本 + 客户端身份 + 能力（放在 `_meta`） | SEP-2575, SEP-2567 |
| 可选发现 | 新增 `server/discover` RPC，一次返回服务器支持的版本、能力、身份；**调用可选** | — |
| 头路由 | Streamable HTTP 请求必须带 `Mcp-Method`、`Mcp-Name` 头，网关可直接按头路由与授权 | SEP-2243 |
| MRTR | 多轮往返请求取代服务端发起的 elicitation / sampling / roots 请求；服务端返回 `resultType: "input_required"`，客户端带 `inputResponses` 重试 | SEP-2322 |
| 可缓存 list | list 响应带 cache hint 与确定性顺序，客户端可缓存工具目录，**保持上游 prompt cache 稳定** | SEP-2549 |
| 扩展框架 | Tasks 正式成为扩展（与 MCP Apps、Enterprise Managed Authorization 并列） | SEP-2663 |
| 授权加固 | RFC 9207 issuer validation；**弃用 Dynamic Client Registration（DCR），改走 Client ID Metadata Documents（CIMD）** | — |
| 正式弃用策略 | **12 个月最低窗口**（加速删除例外 90 天） | — |
| SDK | 四个 Tier 1 SDK（TypeScript / Python / Go / C#）已同步；Rust 为 beta | — |

**被弃用（12 个月窗口）**：roots、sampling、logging、DCR、legacy HTTP+SSE 传输。【二手 tracker，清单项与官方 release post 的单项描述一致，整体清单以 tracker 为准，见 §3-15】

**MCP Roadmap（【一手】modelcontextprotocol.io/development/roadmap，最后更新 2026-08-22）五个优先区**：
1. Agentic messaging primitives（服务端发起事件 / webhooks & channels，取代轮询；Tasks 组合性评审）
2. **HTTP-native transport unification**（目标：Streamable HTTP 作为**唯一**绑定，本地服务器也用 HTTP-over-stdio）
3. **Agent identity + 企业级安全**（DPoP / RFC 9449、Workload Identity Federation、ID-JAG；**明确点名要淘汰"粘贴 API key 与长生命周期 token"**）
4. Improved primitives（统一 `tools/call` 结果契约；**大工具目录的渐进式发现 progressive discovery**）
5. SDK DX

**A2A 的关键原语**（【二手】一致转述）：Agent Card（`/.well-known/agent-card.json`）、Task（状态机：submitted / working / input-required / auth-required / completed / failed / canceled / rejected）、Artifact、`contextId` 做多轮委托分组；v1.0（2026-03-12）引入签名 Agent Card（JWS）与多租户；**规范从未发布正式 registry**（发现靠 Agent Card + 相邻规范）。v1.1 milestone 目标为双向流式，due Oct 2026【未确认已发布，见 §3-14】。

#### 反模式

- **把 MCP 与 A2A 当竞争协议做二选一**——它们是栈的两层。
- **2026 年新项目选 ACP**（已并入 A2A，且 ACP 的 brokered 通信模型与 A2A 的 peer 委托模型不同，迁移是重构不是换 endpoint）。
- **继续依赖协议级 session / `Mcp-Session-Id` 作为状态载体**——2026-07-28 已移除；主流做法是"由工具铸造显式 handle，模型当作参数传回"，而不是把状态藏在传输层。
- **把"合规"当成"安全"**：A2A 的 Task 状态由执行方自报，Agent Card 的 JWS 签名在许多实现中是可选的；["A2A-compliant" 是采购标签，不是安全保证]（【二手】）。
- **继续用粘贴的长期 API key 作为 MCP 身份**（roadmap 已明确列为要淘汰的对象）。

#### 对 MJCode 的可判定判据

| # | 判据（可判定句式） |
|---|---|
| 1.1 | 若项目在 Streamable HTTP 传输上**同时发送 `MCP-Protocol-Version` 头**（取值含 `2026-07-28` 或明确声明的协商版本）→ 判为**对齐**；若只发 `Mcp-Session-Id` 而无 `MCP-Protocol-Version` → 判为**偏离**（官方规范 MUST 项缺失）。 |
| 1.2 | 若项目声明支持的 MCP 版本集合**包含 `2026-07-28`**，或对不含该版本给出显式的"降级路径 + 版本协商错误（`UnsupportedProtocolVersionError`）处理" → **对齐**；若版本清单停留在 `2025-11-25` 及更早且无升级排期 → **偏离**。 |
| 1.3 | 若项目对 `initialize` / `Mcp-Session-Id` 的依赖是**可关闭的**（存在无状态路径），或有明确的"2026-07-28 互操作"测试用例 → **对齐**；若执行流硬依赖握手与 session 才能工作 → **偏离**。 |
| 1.4 | 若项目的 MCP 服务器名 → 工具名映射是**可逆编码**（或入口处禁用分隔符 / 强制字符集校验，使得 `mcp__<server>__<tool>` 可无损反解）→ **对齐**；若存在"拼名后 split 无法还原"的确定性反例 → **偏离**（且属 P1 契约类）。 |
| 1.5 | 若项目对第三方 MCP 工具定义有**版本钉定 + 变更 diff**（至少记录 description 哈希并在 `tools/list` 变化时可见）→ **对齐**；若每次连接都无条件信任最新工具描述 → **偏离**（rug pull 面）。 |
| 1.6 | 若项目**未**把 ACP 作为架构选项，且对"agent ↔ 工具"与"agent ↔ agent"有明确分层说明 → **对齐**；若文档中出现把 ACP 当作在役标准的描述 → **偏离**。 |

### 主线 2 · Skills / 能力分发

#### 结论

- **Agent Skills（SKILL.md）已成为跨平台事实格式**：Anthropic 2025-10-16 首发 → **2025-12-18 以开放标准发布**（agentskills.io）→ 2026 年上半年被 Cursor、OpenAI Codex、Gemini CLI、GitHub Copilot、VS Code 等先后支持。**三级渐进披露（发现 → 激活 → 执行）是这套格式的核心机制，不是可选优化。**
- **更进一步：Agent Plugins 1.0.0（2026-08-06）**把 Skills 与 MCP 服务器打包成一个目录：`plugin.json`（必需）+ `skills/`（可选）+ `mcp.json`（可选）。核心维护者：Amazon、Cursor、Microsoft、OpenAI、Vercel；Google 同日以核心维护者加入。首发支持客户端：ChatGPT、Codex、Cursor、GitHub Copilot、Kiro、VS Code。**Anthropic 不在 TSC 名单内。**（【一手】Vercel 官方文档 + spec 站）
- **AGENTS.md** 是同一族的"项目级指令文件"标准，60,000+ 开源项目采用，现由 AAIF 托管；**Claude Code 2.1.277（2026-09-18）起在无 `CLAUDE.md` 时回退读取 `AGENTS.md`**。
- **但**：Agent Plugins 明确**不定义**安装、分发、权限模型、沙箱、来源验证。没有签名、没有来源证明、没有能力声明——**信任完全由安装它的客户端承担**。

#### 主流做法

**Skill 的最小契约**（【一手】agentskills.io / skill.md 站点）：目录内含 `SKILL.md`（必需），可选 `scripts/`（可执行）、`references/`（按需加载文档）、`assets/`（模板与资源）。
- frontmatter 字段：`name`（必需，≤64 字符，仅小写字母/数字/连字符，首尾非连字符，无连续 `--`，须与父目录同名）、`description`（必需，≤1024 字符）、`license`、`compatibility`（≤500 字符）、`metadata`、`allowed-tools`（**实验性**，空格分隔的预批准工具）。
- **启动成本约 100 token/skill**（仅加载 name + description）；完整指令只在任务命中时才读入上下文。
- 三级披露：① 启动时只加载 name+description → ② 任务匹配时读完整 `SKILL.md` → ③ 按需执行 `scripts/` 或读 `references/`。

**命名空间与分发**：`skills/` 下**每个直接子目录**算一个 skill；规范**禁止递归搜索**（`skills/team/writing/SKILL.md` 不会被加载）。客户端专属内容放在反向域名命名空间目录（如 `com.example.client/`）+ manifest 的 `extensions` 键，其他客户端**必须忽略且不校验其内容**。故障隔离：一个坏掉的 MCP 条目**不得**阻止同插件内 skills 的加载。所有文件解析必须落在插件根目录内（含符号链接解析后），`./` 开头且不可逃逸。

**Plugin manifest 校验**：schema 封闭（`additionalProperties: false`），仅 10 个顶层字段；**只有两个违规是非致命的**（未知顶层字段、`extensions` 非对象 → 报告并忽略后继续）；其余任何违规（缺 `name`、不支持的 `$schema`）**致命，直接拒收且不发现/执行任何组件**。

#### 反模式

- **把 skill 当 prompt 文件**（一次性塞进 system prompt）——渐进披露才是产品本体。
- **默认给第三方 skill 授予与宿主等同的环境权限**（"ambient authority"）——这是最常被跳过、也最危险的一步；`allowed-tools` 只是实验性字段，不能当作沙箱。
- **递归扫描 skills 目录**——规范禁止。
- **把客户端专属配置塞进可移植区域**（`plugin.json` 顶层或 `skills/`）——会直接导致致命校验失败。
- **安装即信任**：多家扫描结论显示社区技能缺陷率在 **26%–37%** 区间（口径不一，见 §3-11）；ClawHub 曾遭 ClawHavoc 活动投放恶意 skill。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 2.1 | 若项目的 skill 加载是**三级渐进披露**（启动只注入 name+description 的索引，命中后才读正文，`scripts/`/`references/` 按需读）→ **对齐**；若在会话启动就把全部 skill 正文注入 system → **偏离**。 |
| 2.2 | 若 skill 目录结构是 `SKILL.md` + 可选 `scripts/ references/ assets/`，且**只识别直接子目录**、不递归 → **对齐**；若用扁平文件表或递归扫描 → **偏离**。 |
| 2.3 | 若项目对 skill 的 `name` / `description` 有**机器化校验**（长度、字符集、与目录名一致）且校验失败即为错误而非警告 → **对齐**；若只做存在性检查 → **偏离**。 |
| 2.4 | 若第三方 skill / 插件执行**默认不继承宿主完整权限**（有独立的权限收窄或进程/文件系统边界）→ **对齐**；若第三方 skill 与内置能力同权同域运行 → **偏离**（P1 级）。 |
| 2.5 | 若项目支持 skill 与 MCP 的**打包分发**（一个目录同时声明 skills 与 mcp 配置，且 MCP 配置不内联进 manifest）→ 判为**对齐 Agent Plugins 方向**；若两者各自独立、无统一包格式 → 判为**未对齐（不阻断，属演进项）**。 |
| 2.6 | 若项目在仓库根目录**能读取 `AGENTS.md`**（至少作为 `CLAUDE.md` 的回退）→ **对齐**；若只认自有私有指令文件名 → **偏离**（跨平台可移植性缺口）。 |

### 主线 3 · 主流 Harness SDK 架构范式对比

#### 结论

**2026 年市场收敛为"厂商原生 SDK"与"独立框架"两阵营**（【二手】多家一致）：

- **厂商原生**：Anthropic Claude Agent SDK（MCP 集成最深，锁 Claude）、OpenAI Agents SDK（handoff 模型最干净，无内置状态持久化）、Google ADK（语言覆盖最广：Python/TS/Java 1.0.0(2026-03-30)/Go 1.0(2026-03-31)，原生 A2A）。
- **独立**：LangGraph（图 + 持久状态 + 时间旅行）、CrewAI（角色团队，最快原型；是唯一同时原生支持 MCP 与 A2A 的独立框架）、Mastra（TS，建于 Vercel AI SDK，agents/workflows/memory/observability/evals 一体）、Vercel AI SDK（统一 TS API，100+ 模型）。
- **AutoGen 已终止演进**：2026-04-03 **Microsoft Agent Framework 1.0 GA**，合并 Semantic Kernel（企业基础设施层）与 AutoGen（多智能体编排层）；**两者同时进入 maintenance mode**（仅安全与严重 bug 修复，无新功能）。社区分支 AG2 继续活跃。

#### 主流做法（六维对比）

| 维度 | Claude Agent SDK | OpenAI Agents SDK | Google ADK | LangGraph | CrewAI | Mastra | Vercel AI SDK |
|---|---|---|---|---|---|---|---|

- **把原型框架直接当生产框架**（CrewAI 原型 → LangGraph / 直调 SDK 生产 是常见路径，但要显式评估）。

### 主线 4 · 上下文工程（Context Engineering）

#### 结论

**主流配方已固定为六件套**，Anthropic 官方文档与工程博客是最完整的一手表述：

1. **把上下文当作有限的注意力预算**——不是"窗口越大越好"，是"最小高信号 token 集"。
2. **JIT（just-in-time）检索**：上下文里只保留轻量标识符（文件路径、已存查询、链接），运行时用工具把数据取进来。
3. **Compaction**：由**服务端**完成（Anthropic compaction，beta header `compact-2026-09-04`），支持按需与 token 阈值两种触发；保留最近若干轮原文。
4. **Context editing**：按规则清除已失效内容（旧工具结果、thinking 块），与 compaction 互补。
5. **工具定义延迟加载 / tool search**：`defer_loading: true` + `tool_search_tool_regex_20251119` / `tool_search_tool_bm25_20251119`，**最多可延迟 10,000 个工具**，默认每次搜索返回 5 个匹配。
6. **子代理上下文隔离**：子代理可以用数万 token 探索，但通常只回传 **1,000–2,000 token** 的压缩摘要。

**prefix cache 复用是与上下文工程绑定的一等约束**（【一手】Anthropic harness 博文）：cached token 成本为 base input token 的 **10%**；原则是 **static first, dynamic last**、用 messages 追加而非改 prompt、**会话内不换模型**（cache 模型相关）、**谨慎增删工具**（工具在缓存前缀里）、**把断点移到最新消息**（多轮应用）、**动态发现用 tool search（追加不破缓存）**。

#### 主流做法

**分层压缩（先 offload 再 summarize）——顺序是有意的**：
- Tier 1 offload：超阈值的工具响应落盘，替换为文件系统引用 + 简短摘要（典型阈值数万 token 量级），**内容仍可按需取回**。
- Tier 2 summarize：上下文继续增长时摘要历史。
- 摘要必须保留的四项：**当前目标 / 已建构或已决定的状态 / 会话中浮现的约束 / 下一步动作**。只记"发生了什么"会导致**目标漂移**。
- 分级降档优于一次性压缩：有实现按上下文预算 70%/80%/85%/90%/99% 分五档逐步降级（warning → observation masking → fast pruning → aggressive masking → full compaction），避免"压缩悬崖"。【二手】
- **Compaction 复用父会话的缓存前缀**：把 `cache_control` 断点放在 system prompt 末尾，压缩后新的一轮仍然便宜。

**Compaction vs Context Reset 的重要区分**（【一手】Anthropic 长任务 harness 博文）：
- compaction = 原地摘要，保留连续性，但**不提供干净起点**；
- context reset = 清空上下文 + 结构化交接产物，给下一个 agent 干净起点。
- Anthropic 发现 Sonnet 4.5 有强"context anxiety"（临近上下文上限就提前收尾），compaction 不够，必须 reset；**但换到 Opus 4.5 后该行为消失，reset 变成死重**。→ **harness 里为补偿模型缺陷而加的东西，必须随模型升级重新验证并剪掉。**

**工具输出截断与规范化**：工具输出是上下文膨胀的最大来源，harness 应在其进入上下文前做后处理（截断到 token 预算、抽取声明需要的字段、剥离样板）。

**结构化记忆槽**：显式定义 goal / constraints / decisions / open questions / current plan step 等槽位并常驻上下文顶部，比让模型从长历史里"自己抽"可靠。

#### 反模式

- **过早压缩**：阈值过低会在上下文仍可导航时就做有损摘要，且摘要漏掉作用域约束 → 目标漂移。Anthropic 建议**从最大召回起步，再向精度迭代**，不要反过来。
- **压缩了指令、留下了噪声**：规则和约束必须保留，被压缩的是历史与证据。
- **offload 后又删掉/移动了落盘内容** → 比留在上下文里更糟（不可恢复）；observation store 必须在整个会话生命周期内存在。
- **把"固定长 system prompt"当成解决方案**：预载很少用到的指令是纯浪费注意力预算。
- **上下文里塞满整个工具目录**（见主线 1 的 progressive discovery 与主线 4 的 tool search）。
- **把为旧模型缺陷设计的补偿机制永久固化**（如 context reset）。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 4.1 | 若项目存在**上下文预算的分层降档机制**（至少 offload 与 summarize 两级，且顺序是 offload 先于 summarize）→ **对齐**；若只有"超阈值一次性截断/摘要"或只有截断无落盘 → **偏离**。 |
| 4.2 | 若摘要/交接产物**显式包含**目标、状态、约束、下一步四项，且有测试或 fixture 校验这四项非空 → **对齐**；若摘要只压缩对话历史无结构化字段 → **偏离**。 |
| 4.3 | 若项目对**工具输出**在进入上下文前做截断/裁剪（有可配置 token 上限），且被 offload 的内容在会话生命周期内可按标识符取回 → **对齐**；若工具输出原样全量入上下文 → **偏离**。 |
| 4.4 | 若项目在每轮请求中**保持稳定前缀**（system prompt 与工具定义顺序确定、不在中途增删工具、不中途换模型），以利 prefix cache 命中 → **对齐**；若每轮工具集/顺序动态变化导致缓存前缀失效 → **偏离**。 |
| 4.5 | 若项目对子代理/子任务的回传结果有**长度上限**（量级 1k–2k token 的压缩摘要）而不是把子任务完整轨迹回灌主上下文 → **对齐**；若子任务完整轨迹进入主循环上下文 → **偏离**。 |
| 4.6 | 若项目对「为补偿特定模型缺陷而加入的机制」（如 context reset / 强制分步）标注了**适用模型与复核触发条件**，并有回归测试证明其在目标模型上仍必要 → **对齐**；若这类机制无条件常驻 → **偏离（死重风险）**。 |

### 主线 5 · 记忆体系

#### 结论

**分层是共识，实现未收敛**（分化点 D5）。

- **类型学共识**：working/short-term（当前窗口）→ episodic（带时间戳的事件日志）→ semantic（抽取的用户/世界事实）→ procedural（学会的流程与技能）。
- **工业实现三条路线并存**：
  - **Mem0**：抽取式（LLM 决定记住什么）+ 双存储（向量 + 图）；**最快上生产**的托管服务；图是增强层而非主基底。
  - **Zep / Graphiti**：**时序知识图**为基底，bitemporal（validFrom/validTo），能回答"T 时刻什么是真的"；适合事实随时间变化的领域。
  - **Letta（MemGPT）**："LLM 即操作系统"，core / recall / archival 三层，**由 agent 自己通过工具调用管理分页**。
  - **Anthropic 的第四种路线**：不做抽取管线，给模型一个**记忆目录**（memory tool，`/memories`，客户端实现文件操作），让模型自己决定写什么；与 compaction 搭配使用。
- **2026 年的生产主流形态**（【二手】一致）：**semantic（向量检索事实）+ episodic（按时间可查的事件日志）为主**，procedural 正在以 skill/指令文件的形式成型。**默认选型是 Postgres + pgvector**（已在跑的关系库上加向量），专用记忆服务只在确有需要时才引入。

#### 主流做法

**先写契约再接 SDK**（这是业界反复强调的顺序）：
1. 定义"什么算一条记忆"（原文轮次 / 抽取事实 / 摘要，还是三者都有——不同定义对应完全不同的下游面积）。
2. **身份作用域**：按 `user_id` / `agent_id` / `(user_id, workspace_id)` 哪个键？跨作用域污染是仅次于陈旧数据的第二大 bug。
3. **真值来源**：抽取器与用户冲突时谁赢？必须有确定性裁决规则（Mem0 原地更新 vs Zep 把矛盾存成边）。
4. **召回触发**：每轮都拉 / 模型主动要 / 启发式？这个选择会以数百毫秒为单位改变延迟画像。
5. **遗忘策略**：**每种记忆类型各自的 TTL**。偏好活得比工单久，工单比工具报错久。
6. **删除路径**：用户要求被遗忘时，能否在 episodic / semantic / procedural 三个面上一次删除？不能就先把缺口写进文档。

**运维要点**：记忆写入**必须异步**，不要让存储延迟影响响应；语义记忆是 PII 风险最高的一层（设计目标就是永久），必须支持显式 update / delete 而不只是 add。

**失败模式（业界反复出现）**：陈旧事实（用户换岗/换栈后旧偏好仍在）、episodic 与 semantic 混存同形、覆盖与更新之间的拉扯（硬删丢审计、软写造重复）、抽取不一致（两个工程师会从同一句话抽出不同记忆 → 先把抽取规则写下来）。

#### 反模式

- **把记忆做成"一个向量库 + 全量历史"**，不区分 episodic / semantic / procedural —— 出问题时无法定位是哪一层错了。
- **记忆只增不删**，无 TTL、无删除路径。
- **在上下文里同时塞入语义事实与时间化事件且共用同一检索路径** → 把持久偏好降格成噪声历史。
- **用语义检索去取短事实与否定句**（"用户不用 Vercel"）——密集检索在这类短事实上是脆弱的；这类更适合指令文件或结构化事实存储。
- **同步写入阻塞响应**。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 5.1 | 若项目的记忆分层**至少区分**"会话内工作记忆 / 跨会话持久记忆"两层，且每层有独立的**配额与写入策略** → **对齐**；若只有一层持久存储、靠检索长度硬截 → **偏离**。 |
| 5.2 | 若每条记忆条目**可指明其所属层与作用域**（user / project / session 或等价键），且跨作用域读取有显式校验 → **对齐**；若记忆条目只有内容与向量、无作用域标记 → **偏离**（跨用户污染面）。 |
| 5.3 | 若项目对持久记忆有**遗忘策略**（TTL 或容量闸 + 淘汰规则），且淘汰规则是确定性的（有测试）→ **对齐**；若只增不删、靠容量硬截 → **偏离**。 |
| 5.4 | 若项目提供**删除路径**：给定用户/项目标识可一次删除其全部记忆（含派生索引），并有测试证明删除后检索不到 → **对齐**；若删除只覆盖主表、索引残留 → **偏离**。 |
| 5.5 | 若记忆写入是**异步/不阻塞主响应**（或显式声明同步写入并有超时与降级）→ **对齐**；若记忆写失败会阻断或显著拖慢对话 → **偏离**。 |
| 5.6 | 若项目**不把**"抽取的事实"与"带时间戳的事件"存成同形、同检索路径 → **对齐**；若两者共用同一张表同一套检索 → **偏离**（诊断不可分）。 |
| 5.7 | 若项目的记忆注入量**受预算约束**并可与上下文预算统一核算（注入 N 条、最多 M token，有常量可查）→ **对齐**；若注入量随库大小无界增长 → **偏离**。 |

### 主线 6 · 多智能体编排

#### 结论

**2026 年的收敛结论是明确的：「单主循环 + 一次性隔离子代理」胜过多角色自由编排。**

- **已收敛到该形态的实现**：Anthropic 的多智能体研究系统、Claude Code 的 Task/子代理、OpenAI 的 agents-as-tools、Cognition 2026-03 的 Managed Devins、Microsoft Agent Framework。
- **peer 协作（GroupChat / swarm）在 2026 年明显失势**。标志性事件：Cognition 2025-06 发《Don't Build Multi-Agents》（主张单线程 + 独立压缩 LLM），**九个月后的 2026-03 自己发布了 Managed Devins**（协调者把工作分派给各自独立 VM 里的受管 Devin），理由正是 Anthropic 用过的同一条隔离论证——"上下文累积、注意力退化、每个子任务质量下降"。
- **成本是硬约束**：Anthropic 自述多智能体运行约为 chat 方式的 **~15× token**。【二手转述】另有 2026 年生产基准称独立 peer 约 **+58%**、集中式约 **+285%** token 开销，且在**同等总思考 token 预算**下单智能体常能持平或胜过多智能体（arXiv 结果转述）。→ **归一化算力后，多智能体的相当一部分优势会消失。**
- **形态分布（【二手·单一来源】）**：orchestrator-worker 约占生产多智能体部署的 ~70%。**该数字仅作趋势参考，不作判据。**

#### 主流做法

**四种可选拓扑 + 选择规则**：
- **Supervisor / hierarchical**：一个协调者分解并分发，聚合结果。优点是可审计、可按分支设预算；代价是协调延迟（三层 × 2s = 6s 起）。
- **Orchestrator-worker（生产默认）**：一层路由 + 专业化 worker 并行。
- **Swarm / 共享黑板**：无中心控制，靠共享状态涌现。适合天然并行/幂等/需要对抗验证的工作；**受监管领域（金融、医疗、EU AI Act Annex III）通常不可辩护**，因为没有单一 trace 能说明系统如何得出输出。
- **Sequential pipeline**：步骤确定且确定性 → 别用 agent，用普通工作流运行时 + 若干 LLM 调用。

**交接（handoff）的工程纪律**：
- **typed payload**：用 JSON Schema / Pydantic / Zod 定义 agent 间消息，两端都校验——这是多智能体系统里杠杆最高的单一纪律。
- **不要在每个 hop 转发完整历史**：20,000 token 的历史灌进每个 worker 既贵又噪；主流做法是编排层持有类型化上下文对象，**每个 worker 只拿相关字段（典型 200–500 token）**。
- **交接深度设硬上限**：需要 4–5 跳以上的任务几乎必失败。
- **交接载荷携带 `trace_id`**，端到端可观测。
- **终止条件**：每一层（manager 和 worker）都要有 max-step、max-cost、max-wallclock 三重上限，并在触达前告警。
- **编排逻辑放在 agent 之外的确定性代码里**：不要让 agent 自己决定是否派生子代理。
- **共享状态尽量 append-only**，agent 间用不可变消息传递而非共享可变数据。

**OpenAI 的侧证**：2026-04-15 的 Agents SDK 更新把 `nest_handoff_history` 改为**默认 opt-in（关闭）**，目的就是减少跨 agent 上下文串味。【二手】

#### 反模式

- **为多智能体而多智能体**：说不出是"子任务本质不同 / 并行能提吞吐 / 质量需要复核"三条中的哪一条，就不需要拆。
- **自由格式 agent 间聊天**：token 爆炸 + 可观测性崩塌。
- **共享记忆无政府状态**：每个 agent 读写同一块 scratchpad → 竞态 + 注入面 + 不可调试。
- **无终止条件**。
- **只有 per-agent eval，没有系统级 eval**——多智能体是在**接缝处**失败的，eval 必须是端到端的。
- **"三省六部幻觉"**：把多个 agent 命名为产品经理/架构师/测试工程师，让它们像公司部门一样传文档协作。三条反驳：① LLM 没有人类的注意力与专业壁垒限制，贴标签不会让它更专业，只会让它拒绝越界，而最有价值的推理常发生在边界上；② **信息在流转中死亡**——A 传给 B 的是结论不是推理过程，每跳都在累积误差，最终"局部正确、整体漂移"；③ Anthropic、OpenAI、Google 自建 agent 系统**没有一家采用这个模式**，都用 orchestrator-worker + 外部状态文件。【二手，2026 年高讨论度反模式】

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 6.1 | 若项目存在**单一的编排权威**（一个编排者/主线程持有完整上下文与计划），工作单元是**一次性、上下文隔离的子任务**，且只回传压缩结果 → **对齐主流收敛形态**；若存在子任务之间直接互相发消息、共同修改共享可变状态的通道 → **偏离**。 |

| 6.6 | 若"是否派生子任务"由**确定性代码**决定，而非交给模型自行决定 → **对齐**；若模型可自行无限派生 → **偏离**。 |
| 6.7 | 若项目的多智能体/编排层存在**端到端（系统级）eval**，而不只是各组件单测 → **对齐**；若只有 per-agent eval → **偏离**（接缝处无守护）。 |
| 6.8 | 若项目的角色/岗位设定是**能力裁剪与提示分工**（工具子集 + 角色提示注入 system）而非"让 agent 扮演公司部门互相评审" → **对齐**；若多角色之间存在文档传递式流水线且无编排者持有全局上下文 → **偏离（三省六部反模式）**。 |

### 主线 7 · 安全与沙箱

#### 结论

**fail-closed 已是事实标准表述，并在多家官方实现中落到具体开关。** 四个控制面（身份 / 作用域 / 组合 / 指令-数据边界）缺一不可，且**鉴权是必要不充分条件**。

**权威框架的现状**：
- **OWASP**：《Top 10 for Agentic Applications 2026》（100+ 安全研究者参与），把 MCP tool poisoning 归入头号风险 Goal Hijacking；另有专门的 MCP Tool Poisoning 攻击条目页【一手 OWASP 社区页】。
- **NSA**：AI Security Center 于 **2026-05-20** 发布 *MCP Security Design Considerations*，指出协议扩散速度超过其安全模型，要求明确信任区、最小权限、部署前严格评审。【二手转述】
- **CISA**：2025-05 联合指南，把 AI agent 基础设施纳入 SOC 必须监控的攻击面。【二手转述】
- **监管时钟**：Colorado AI Act 2026-06 可执行；EU AI Act 高风险义务 2026-08 落地。【二手】

#### 主流做法

**（a）权限分级 permission tiers**
- OpenAI 官方做法：给每个工具按 **low / medium / high** 打风险分，依据只读 vs 写、可逆性、所需账户权限、财务影响；用风险分触发自动化动作（高危执行前暂停做 guardrail 检查，或升级给人类）。
- Claude Agent SDK 的六步判定链：**Hooks → Deny 规则 → Ask 规则 → 权限模式 → Allow 规则 → `canUseTool` 回调**，顺序本身是安全保证的一部分。要点：
  - **Hooks 最先执行，且 hook 的 deny 即使在 `bypassPermissions` 下也生效**；
  - **被 allow 规则放行的调用永远到不了 `canUseTool`** → 想"每次都跑"的检查必须写成 PreToolUse hook，不能写在回调里；
  - **deny 规则跨层级累加**，全局 deny 不能被项目 allow 覆盖；
  - hook 退出码语义：0 = 通过（后续权限流仍走）、**2 = 阻断**（stderr 回给模型）、其它 = 非阻断错误（记录但放行）。

**（b）OS 级沙箱**
- Claude Code / Claude Agent SDK：`sandbox.enabled`（macOS 用 **Seatbelt**，Linux 用 **bubblewrap**）+ `sandbox.filesystem.allowRead/allowWrite/denyRead/denyWrite` + `sandbox.network.allowedDomains`。
- **fail-closed 的具体开关**：`sandbox.failIfUnavailable: true`（隔离环境不可用即失败）、`sandbox.allowUnsandboxedCommands: false`（关掉 `dangerouslyDisableSandbox` 出口）、`sandbox.credentials.files/envVars` 的 `mode: "deny"`。
- 沙箱能扛住 prompt injection：模型被说服去删家目录，沙箱在系统调用层面硬拦。
- 组织级：在 managed settings 层禁掉 `bypassPermissions`（该层不可被任何下层覆盖）。

**（c）HITL 审批**
- ADK：`request_confirmation` 作为工具，模型在动作前必须调用它。
- Claude SDK：`canUseTool` 回调 / `PermissionRequest` hook。
- OpenAI Agents SDK：Guardrails（input / output / tool 三类）→ `tripwire_triggered` 立即抛异常终止；`require_approval` 做 HITL；Microsoft Agent Framework：`ctx.request_info()` 暂停 + `@response_handler` 恢复，**HITL 是一等公民**。

**（d）SSRF 防护**
- **默认拒绝出口 + 精确 allowlist**：这条单一控制就能中和大部分注入成功后的外泄与 C2。
- 阻断 link-local 与私有网段，**必须包含 IPv6**：`169.254.169.254`（IMDS）、`fd00:ec2::254`（AWS IPv6 metadata）、CGNAT 段、IPv4-mapped 形式。
- **resolve-then-validate**：先解析再校验、**对已连接地址做决策**，否则 DNS rebinding 可绕过；不要只信 URL 字符串。
- **按 sink 分别设策略**（一个共享 allowlist 会导致浏览器工具拿着连接器的凭据去访问伙伴 API）；文档渲染器与代码沙箱**彻底不给网络**。
- **canary 测试矩阵进 CI**：canary token 一旦出现在模型 transcript 里即判失败，即使没有 deny 日志。
- **2-of-3 规则**（设计定律）：**能读文件、能上网、能写代码——三者只能同时持有其二**。

**（e）MCP 供应链与工具层**
- **Tool poisoning vs rug pull**：前者是工具元数据一开始就藏恶意指令；后者是先干净、拿到信任后再改定义。**因为多数客户端在连接时重新拉取工具定义且不钉定/不 diff，这个替换可以是不可见的。**
- 控制：钉定版本并验签/校验哈希（Sigstore 式来源证明优先）；**每次 `tools/list` 都校验工具描述哈希**（OWASP 推荐）；diff 版本间描述——**描述变更即行为变更**；维护 SBOM 式清单；CI 里跑 MCP 安全扫描。
- 凭据：**OAuth 2.1 + PKCE**；**按 RFC 8693 做 token exchange，绝不透传 token**；服务间 mTLS 并校验 audience/scope；每个 server 用最小权限、短生命周期凭据；能传播终端用户身份就传播。
- **审计**：每次调用落结构化日志（ts / principal / token_id / tool / args / decision / scope_checked / session / result / latency），**ship 到 append-only 或 WORM 存储**，使被攻陷的服务器无法改写历史；告警模式：denied-scope 尖峰、异常调用序列（read-private 后 write-external）、量级异常、重复校验失败。
- **被阻断时把安全结果作为工具输出返回给模型**（"检测到 prompt injection"），避免模型在同一调用上死循环重试。
- **不要只依赖 system prompt 做限制**——必须在工具执行层实现访问控制。

#### 反模式

- **fail-open 默认值**（能力交集为空时放行、沙箱不可用时降级为无沙箱继续执行、工具未登记风险级时按最宽松处理）。
- **只做安装时扫描**——"扫过一次是干净的"挡不住 rug pull；Postmark MCP 事件（2026-09，【二手】）中包先正常发布，后续版本静默 BCC 全部外发邮件到攻击者域名。
- **把安全限制写在 system prompt 里**当作访问控制。
- **用长期、宽作用域的 token**（token sprawl 是多数具名事件的根因）。
- **给文档渲染器/代码沙箱保留网络**（silent fetch：没有工具调用就没有日志行，也就没有告警）。
- **审计日志留在可被攻陷的同一台主机上**。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 7.1 | 若每个工具都有**显式风险分级**（至少 3 档：只读 / 写 / 不可逆或高危），且分级被**审批与沙箱决策真实读取**（不是只写不读）→ **对齐**；若存在"未登记即默认某档"的静默回落路径且该回落无门禁守护 → **偏离（P1）**。 |

| 7.7 | 若对**出站网络**有默认拒绝 + 显式 allowlist，且阻断清单**覆盖 IPv6 与 link-local**（含 `169.254.169.254`、`fd00:ec2::254`）→ **对齐**；若只校验 URL 字符串、只覆盖 IPv4 私有段 → **偏离**。 |
| 7.8 | 若对 URL 类工具做**resolve-then-validate**（对解析后的连接地址决策，而非对主机名决策）→ **对齐**；若只对请求前的主机名做校验 → **偏离**（DNS rebinding 面）。 |
| 7.9 | 若第三方工具定义有**钉定 + 哈希校验/变更可见**（`tools/list` 变化可被检测）→ **对齐**；若每次连接无条件采信 → **偏离**。 |
| 7.10 | 若每次工具调用产生**结构化审计记录**（含 principal / tool / args 摘要 / decision / scope），且该记录**写入不可被 agent 改写的存储** → **对齐**；若审计只存在于应用日志、可被同源进程改写 → **偏离**。 |
| 7.11 | 若"读文件 / 联网 / 写代码"三者不会在同一执行上下文中**同时全开**（2-of-3）→ **对齐**；若同一默认配置同时具备三者 → **偏离**。 |

### 主线 8 · 持久化与长时运行

#### 结论

**"崩溃后能从断点继续"在 2026 年已是 table stakes**，但**机制分两派、尚未统一**（分化点 D2）：

| | 状态快照（checkpointer） | 持久执行（replay） |
|---|---|---|
| 代表 | LangGraph InMemory/SQLite/Postgres saver | Temporal、DBOS、Restate、Inngest |
| 保存什么 | 每个 super-step 后的**全图状态快照** | 每个步骤结果的**有序事件历史** |
| 恢复方式 | 载入最后快照，从待执行节点继续 | **重放代码**，已完成步骤返回记录结果 |
| 持久化单元 | super-step | 单个 activity / step |
| 主要风险 | **非幂等副作用在重执行的节点里触发两次** | **任何留在编排代码里的非确定性调用会破坏重放** |
| 正确性归谁 | 你，在节点边界（幂等键） | 引擎（但要求你服从它的控制流） |
| 适合 | 对话型 agent、HITL 暂停、快速采用 | 长周期工作流、严格 exactly-once 副作用 |

**共同铁律只有一条：绝不重放非确定性步骤。** agent 的持久化单元是 **observation**（它已经看到的每一个工具结果与模型 completion）——因为那是重跑唯一无法复现的状态。

**Anthropic 的架构表态（【一手】Managed Agents 工程博文）**：把 agent 虚拟化成三个接口——**session（append-only 事件日志）**、**harness（调用模型并把工具调用路由到基础设施的循环）**、**sandbox（执行环境）**；三者可独立失败与替换。harness 移出容器、以 `execute(name, input) → string` 调用容器（容器成为 cattle）；harness 崩溃后用 `wake(sessionId)` + `getSession(id)` 从最后一个事件恢复。**"不要养 pet"。**

#### 主流做法

- **事件溯源 / append-only 事件日志 + 投影**：每个 run 一条 append-only 日志（"step started" / "step completed with result"），通常落在 Postgres。
- **SQLite WAL 是本地/桌面形态的默认**：OpenAI Agents SDK `SQLiteSession`、LangGraph `SqliteSaver`、Mastra LibSQL。
- **幂等键必须从稳定身份派生**：`idempotency_key = f"{run_id}:{step_id}"`，**而不是在重试路径内部生成的值**。验证方法：故意在副作用返回后、函数返回前 `process.exit(1)`，重启后下游服务应记录**两次请求、同一个幂等键、一次实际效果**。
- **checkpoint ≠ memory**：memory 帮 agent 回答下一个问题，checkpoint 说明当前任务哪些步骤已完成；checkpoint 无法冻结一次在途的模型调用，也无法撤销已发出的邮件。
- **运行属于 runtime，不属于浏览器/UI**：浏览器连接不应持有工作，也不应是 run 完成或被计费的前提；UI 通过 SSE 订阅事件并在重连时接着收（Copilot coding agent、云端 Codex 即此形态）。
- **规模化验证**：杀掉 worker 中途、部署期间跑、一次发一千个 run——都能测。
- **LangGraph 的 O(N²) 问题与解法**：默认全量快照下，200 轮编码 agent 会向 checkpointer 序列化 **5.3 GB**；LangGraph 1.2 的 `DeltaChannel`（每步只写增量 + 每 K 步一次全量快照，Deep Agents 默认 K=50）降到 **129 MB**，且恢复延迟有界。

#### 反模式

- **把重试当成恢复**（retry = 从头 = 再次扣款）。
- **把非幂等副作用和模型调用放在同一个持久化单元内**（快照派下会重复触发；重放派下会触发非确定性错误）。
- **把 LLM 调用直接写在重放式编排代码里**（必须放进 Activity）。
- **让 run 生命周期依赖浏览器/渲染进程存活**。
- **幂等键在重试路径内生成**（每次重试生成新键 → 重复扣款）。
- **只存快照、不存事件**（无审计、无重放、无法回答"第 12 步为什么这么走"）。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 8.1 | 若项目存在 **append-only 的事件链/事件日志**（每条 run 的事件按序、不可改写），且可从任意事件点重建状态 → **对齐**；若只有可变状态表、无事件序列 → **偏离**。 |
| 8.2 | 若 run 的生命周期**独立于渲染进程/窗口**（关闭 UI 后 run 仍能完成；重连后能接着消费事件）→ **对齐**；若 UI 断开即 run 中断 → **偏离**。 |
| 8.3 | 若项目能**从中断点恢复**（有可枚举的恢复入口，且"恢复"不等于"重跑"），并有自动化测试覆盖"中途崩溃 → 恢复 → 副作用不重复" → **对齐**；若无恢复入口或恢复等价于重跑 → **偏离**。 |
| 8.4 | 若所有**不可逆副作用**都有从 `run_id` + `step_id` 派生的**幂等键**（而非运行时随机生成）→ **对齐**；若幂等键在重试路径内生成 → **偏离**。 |
| 8.5 | 若持久化后端**至少有一个落盘实现**（SQLite WAL / Postgres / LibSQL 等）且为默认或可一键切换 → **对齐**；若仅内存态 → **偏离**。 |
| 8.6 | 若检查点/快照的存储增长**有上界策略**（增量或周期性全量，非每步全量），或已量化说明其增长模型 → **对齐**；若每步全量快照且无上界说明 → **偏离（规模化风险）**。 |
| 8.7 | 若"session / harness / sandbox"三者在架构上**可独立失败与替换**（harness 崩溃后可从 session 事件恢复，sandbox 崩溃可作为一次工具错误被捕获）→ **对齐**；若三者强耦合于单一进程/容器 → **偏离**。 |

### 主线 9 · 可观测与评估

#### 结论

- **OTel GenAI 语义约定：可用、应采用，但尚未稳定。以一手仓库状态为准。** 语义约定主仓 v1.42.0（**2026-06-12**）发布说明明确："All `gen_ai.*` attributes, metrics, events, and spans have been deprecated and moved to the dedicated OpenTelemetry GenAI Semantic Conventions Repository"；新仓 `open-telemetry/semantic-conventions-genai`（创建于 2026-05-05）**截至 2026-10-12 零 tagged release、零 published release**，全部文档标记 `Status: Development`。**存在多家厂商博客宣称"2026-06 已稳定"，与一手仓库状态冲突 → 以一手为准（见 §3-1）。**
- **实践结论不变**：OTLP 传输与 tracing 模型（span / 父子关系 / resource attributes）是稳定的，**应作为默认**；需要谨慎的只是 `gen_ai.*` 的字段名与形状——**钉版本 / 钉 commit，并预期会动**。
- **评估（eval）的主流形态是三层管线**：离线 golden 集（每个 PR）+ staging 全量门禁（发布前）+ 线上采样监控（带漂移检测）。**少任何一层都会稳定地漏掉本可捕获的回归。**

#### 主流做法

**（a）OTel GenAI 语义约定要点**（以当前仓库为准）
- 属性：`gen_ai.provider.name`（取代已弃用的 `gen_ai.system`，但 2026 年**建议两者都发**，许多 collector/dashboard 仍读后者）、`gen_ai.operation.name`（`chat` / `text_completion` / `embeddings` / `execute_tool` / `invoke_agent` / `create_agent` / `plan` / `invoke_workflow` / `retrieval`）、`gen_ai.request.model`、`gen_ai.response.model`、`gen_ai.response.finish_reasons`、`gen_ai.usage.input_tokens` / `output_tokens`、`gen_ai.conversation.id`、`gen_ai.tool.name`、`gen_ai.tool.call.id`、`gen_ai.agent.name`。
- span 命名：`{gen_ai.operation.name} {gen_ai.request.model}`，如 `chat gpt-4o-mini`；SpanKind = CLIENT（没有独立的 AI tracing 协议，因此任何 OTLP 后端都能收）。
- 指标：`gen_ai.client.token.usage`、`gen_ai.client.operation.duration`（直方图）。
- MCP 子规范：`mcp.client` / `mcp.server` span，属性 `mcp.method.name`、`mcp.protocol.version`、`mcp.session.id`；**推荐用它而非通用 RPC 语义约定**。
- **内容捕获是 opt-in 且敏感**：prompt / completion / 工具参数默认关闭（如 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true` 才开），规范明确警告这些字段"可能包含用户/PII 数据"。
- 兼容开关：`OTEL_SEMCONV_STABILITY_OPT_IN`（新旧属性形状过渡期）。
- **成本不是标准字段**：token 数 join 你的模型价目表自行推导。

**（b）三层 eval 管线**
- **离线开发套件**：golden 数据集，每个 PR 跑；确定性校验器 + 快速 LLM judge 住在这一层。**Anthropic 建议从 20–50 个真实失败用例起步**，不要等凑够几百条。
- **Staging 门禁**：发布前跑全量 golden 集；这一层跑一致性测试（`pass^k`）、轨迹评估、对抗/红队。不通过不部署。
- **线上生产监控**：采样线上流量 + 漂移检测；低分交互自动标记人工复核，并**自动回流进下一迭代的开发 eval 集**（闭环）。

**（c）LLM-as-judge 的正确用法**
- 基础结论（Zheng et al. 2023）：GPT-4 judge 与人类约 **85%** 一致，人类之间基线约 **81%**。
- 已知偏差：位置偏差、冗长偏差、自我偏好、格式风格偏差。
- 2026 最佳实践栈：**用若干小模型组成 jury 而非单个大模型**；**用人工标注 golden 集校准 jury**；**用两两比较而非逐点打分，并交换顺序取平均**以抵消位置偏差；写清晰 rubric。
- **关键警告：judge 之间高一致 ≠ 与人类对齐**。一致性只说明稳定，**只有对人类的校准能说明它是对的**。judge 是可扩展打分器，不是标准制定者。

**（d）工具格局（【二手】）**
- LangSmith（LangChain/LangGraph 栈，trajectory 评估经 `agentevals`/`openevals`，线上 eval 带漂移检测）
- Braintrust（eval-first，开源 autoevals；CI 集成可在指标跌破阈值时**阻断 PR**——最接近"eval 成为真门禁"的实现）
- DeepEval / Confident AI（pytest 风格；**Tool Correctness 是确定性指标，适合 CI**；DeepTeam 红队模块映射 OWASP Agentic Top 10）
- Promptfoo（配置优先的红队；**2026-03 被 OpenAI 收购，仍 MIT**）
- Ragas（RAG 专用：context precision/recall、faithfulness、answer relevance）
- Arize Phoenix（OTel 原生，~11k stars）、Comet Opik（完全开源可自托管，~21k stars）、MLflow、Galileo、Maxim、W&B Weave
- **重要提醒**：OpenAI 平台 **hosted Evals 产品**（与开源 `openai/evals` 仓库不同）**正在下线**：2026-06-03 宣布，**2026-10-31 转只读，2026-11-30 彻底关闭**；官方引导迁往 promptfoo。

**（e）已知盲区（规范尚未解决，须自建）**
1. **多智能体协调语义**：每个调用都有 span，但"这两个 agent 在争论同一个任务"无法表达——委托/交接语义未标准化。
2. **按业务工作流的成本归因**：finance 不问"span 4f2a 烧了多少 token"，而问"发票处理工作流上月花了多少"——需自行加 workflow 标识并聚合。
3. **推理路径**：span 能说明 agent 调了 refund 工具，但回答不了"为什么走这条路"。

**（f）基准的诚实用法**：公开基准只用于定位，不作裁决。**tau-bench 的 `pass^k` 是值得内化的一条**：前沿 agent 单次成功率 <50%，`pass^8` <25%——**可靠性而非能力是那堵墙**；只跑一次的 benchmark 恰好掩盖了这件事。**eval 饱和**：套件接近 100% 时它就不再有用于改进，正确反应是加更难的题，不是庆祝。**Anthropic 的教训**：CORE-Bench 上是**评估集的 bug 而非模型 bug** 让 Opus 4.5 从 42% 变 95% → **必须校验你的评估器本身**。

#### 反模式

- **把 `gen_ai.*` 当冻结契约硬编码进长期存储的 schema**。
- **只测 prompt，不测"组装后模型实际看到什么"**（正确的 eval 对象是 assembled context，不是 prompt 字符串）。
- **judge 未对人工 golden 集校准**就当标准用。
- **只有 per-agent eval，没有端到端系统级 eval**。
- **eval 不进 CI**（只做 `--check` 的 schema/fixture 校验而真跑不触发 → 门禁假闭环）。
- **用公开 benchmark 分数当作自己系统的结论**。
- **默认开启 prompt/completion 内容捕获**而不做脱敏与留存设计。

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|

| 9.9 | 若项目的 eval 指标**包含可靠性维度**（同一任务重复 k 次的成功率 / `pass^k` 或等价指标），而不只是单次通过率 → **对齐**；若只报单次成功率 → **偏离**。 |
| 9.10 | 若 trace 携带**跨层关联标识**（一次 run / workflow / conversation 的 id，能把编排、记忆、推理、工具执行串成一棵树）→ **对齐**；若各层各自发日志、无共同 id → **偏离**。 |

### 主线 10 · 共识与反模式

#### 结论

**「Agent = Model + Harness」是 2026 年的行业共识表述，且有权威出处。**

- **Anthropic 的一手表述**：在 SWE-bench 语境下，"an 'agent' refers to **the combination of an AI model and the software scaffolding around it**"；该 scaffolding "responsible for generating the prompts that go into the model, parsing the model's output to take action, and managing the interaction loop"。Claude Code 官方文档把 Claude Code 描述为 "**the agentic harness around Claude**"，它"provides the tools, context management, and execution environment that turn a language model into a capable coding agent"。
- **量级佐证（【二手·论文转述，见 §3-9】）**：VILA-Lab 对 Claude Code v2.1.88 的逆向统计——约 **512,000 行 TypeScript、1,884 个文件**，其中**仅 1.6% 是 LLM 产出的决策逻辑**，98.4% 是基础设施：54 个内置工具（19 无条件 + 35 按功能开关）、7 种权限模式、5 层上下文压缩管线、27 种 hook 事件、7 层独立安全栈。论文主张："**随着基础模型的基线推理能力趋同，自主系统可靠性的关键差异项变成模型周围那套确定性工程 harness。**"
- **Harness 不是临时脚手架，而是持续工程学科**（【一手】Anthropic）：演进顺序是 **Prompt → Context → Harness**，每一步都在扩大工程边界。关键洞察：**更好的模型不会让 harness 消失，只会扩大运行包络**——更强模型 → 更雄心任务 → 新失败模式 → 更好的 harness。因此 Anthropic 明确要求**周期性复查 harness 中"模型做不到所以由我们代劳"的每一条假设并剪掉死重**（例：为 Sonnet 4.5 的 context anxiety 加的 reset，在 Opus 4.5 上变成死重）。
- **失败归因**：Forrester 2026-03 称 88% 的企业 agent 试点从未进入生产；进入生产但无法扩展的失败中，41% 缘于成功标准不清、33% 缘于工具/数据访问不足、26% 缘于评估漂移——**没有一项是模型智能问题，全是 harness 问题**（【二手】）。

#### 主流做法（正面清单）

1. **用模型已经很熟的工具**（bash + 文本编辑器这类），而不是为 agent 发明新抽象。
2. **把编排决策交还给模型**：给代码执行工具，让模型自己决定过滤/管道化结果，而不是 harness 硬性规定"每个工具结果都要过一遍上下文"。
3. **提升为专用工具的判据是明确的**：需要安全边界 / 需要呈现给用户 / 需要可观测（类型化参数才能 log、trace、replay）。可逆性常是好判据——难逆的动作（外部 API 调用）用人类确认拦住。
4. **让模型自己管上下文**：skills（渐进披露加）、context editing（选择性删）、子代理（fork 新窗口隔离）、memory folder（自己写）。
5. **定期剪枝**：问"我能停止做什么"。
6. **结算级 checklist**：先问"这个 AI 的护栏够不够成熟"，而不是只问"模型够不够聪明"。

#### 反模式（汇总清单，按出现频率）

| 类别 | 反模式 |
|---|---|
| 架构 | 为多智能体而多智能体；过度工程（planner/router/gateway 层层叠加却拿不出每层的收益指标）；"三省六部幻觉"（agent 扮演公司部门、文档传递式流水线） |
| 通信 | 自由格式 agent 间聊天；共享记忆无政府状态；无终止条件（max-step / max-cost / max-wallclock） |
| 上下文 | 过早压缩；压缩指令却留下噪声；offload 后又删除落盘内容；把长 system prompt 当解法；预载全量工具目录 |
| 记忆 | 不分层；只增不删无 TTL；episodic 与 semantic 同形同路；同步写入阻塞响应 |
| 安全 | fail-open 默认值；安全限制只写在 system prompt；长期宽作用域 token；只做安装时扫描；审计日志留在可攻陷的主机 |
| 持久化 | 把重试当恢复；非幂等副作用与模型调用共处一个持久化单元；LLM 调用直接写在重放式编排代码里；run 生命依赖 UI |
| 评估 | 只测 prompt 不测 assembled context；judge 未校准；只有 per-agent eval；eval 不进 CI；用公开 benchmark 当自家结论；默认开启内容捕获 |
| 治理 | 安装即信任第三方 skill / MCP；把"协议合规"当"安全保证" |

#### 对 MJCode 的可判定判据

| # | 判据 |
|---|---|
| 10.1 | 若项目的文档与实现**明确区分"模型能力"与"harness 职责"**（存在一处把 loop / tools / context management / guardrails 归为 harness 的权威描述）→ **对齐共识表述**；若把 agent 行为一律归因于模型 → **偏离**。 |
| 10.2 | 若项目对每一条"为补偿模型缺陷而加入的机制"都有**适用条件标注 + 复核触发条件**（模型升级即重验）→ **对齐**；若这类机制无条件常驻且无回归测试 → **偏离（死重）**。 |
| 10.3 | 若项目在新增任何一层（新的 planner / router / 中间件）时**要求给出该层的收益指标**，且存在不使用该层也能跑通的路径 → **对齐**；若架构层数只增不减、无收益论证 → **偏离（过度工程）**。 |
| 10.4 | 若项目存在**"先工作流，后 agent，最后才多智能体"的选型记录的痕迹**（即简单任务走确定性路径而非一律走 agent 路径）→ **对齐**；若所有请求一律进入 agent 循环 → **偏离**。 |
| 10.5 | 若项目的能力扩展（新工具/新技能/新 MCP）**必须过登记门禁**，且门禁是**逐项全覆盖**而非只查孤儿 → **对齐**；若新增能力可绕过登记静默生效 → **偏离（假闭环）**。 |
| 10.6 | 若项目对"对外声称的能力"与"机器守护的不变量"有**一一对应清单**，且清单中不存在"文档声称但无守护"的条目 → **对齐**；若存在声称与守护的落差且可被反例击穿 → **偏离（半截实现）**。 |
