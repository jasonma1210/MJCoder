# 定时任务通道接入 V 层（设计 + 实现）· 2026-10-18

> 起因：第三轮审查结论「定时任务通道无 V 层入口」是三个已知缺口之一，卡在一个产品决策上：
> **是否接受每个任务多一次模型调用**。本文先把行业口径摆出来，再给落地形态与成本模型。
> 实现提交：`main/verifyPolicy.js`、`main/scheduledVerify.js`（新增），`main/verifyRun.js`、
> `main/main.js`、`main/scheduler.js`（改造）。

---

## 1. 结论先行

**「每任务一次额外模型调用」是个伪二选一。** 主流没有任何一家对定时任务全量跑模型判分；
它们的共同结构是：

| 层 | 成本 | 什么时候跑 | 我们对应 |
|---|---|---|---|
| 确定性校验（测试/断言/台账对账） | ≈0 | **全量必跑** | L1（`verifier.js`） |
| 模型判分（judge / guardrail） | 一次调用 | **按风险或抽样** | L3（`verifierL3.js`） |
| 人工确认 | 一次点击 | **只在不可逆动作** | 定时任务的审批档 + 交付降级 |

所以本实现取 **L1 全量 + L3 条件触发 + 无人值守 fail-closed**，而不是「全开」或「全关」。

---

## 2. 行业口径（2026-10 调研）

| 类型 | 代表 | 校验靠什么 | 无人值守如何处理审批 | 每任务额外模型调用 |
|---|---|---|---|---|
| 消费级定时助手 | ChatGPT Scheduled Tasks | 基本不校验，产物是通知 | 需要授权的外部动作 → **任务自动暂停**并提醒；长期无人互动 auto-pause | 无 |
| 工作流引擎 | n8n / Dify / Coze | 节点级成功 + 结构化输出 | `waiting_human` 节点；超时升级或搁置 | 无（LLM 只在该判断的节点） |
| 后台编码 Agent | Cursor BG / Copilot coding agent / Codex / Devin | **跑测试和 build**（确定性），产物是 PR | 不需要暂停：人工审查在 merge 前 | 无 |
| 带 guardrail 的框架 | OpenAI Agents SDK / LangGraph | **第二个模型做 input/output 检查**，tripwire 硬停 | 持久化 interrupt，异步等人 | **有，每 turn 一次** |

三条可复用的共识：

1. **校验分两层，成本结构完全不同**：确定性检查永远跑；模型判分只在安全/合规、离线评测、抽样复检三处开。
2. **抽样率有公开经验值**：n8n 生态的口径是「离线全量、线上抽 5–10%、确定性指标全量」。
3. **没人用「事后判分」兜无人值守的风险**：真正的保障是**把不可逆动作挪出自动执行**。

来源：ChatGPT 计划任务边界（toolnavs.com/zh/article/1925）、Agents SDK guardrails 与成本（bluebear.ai）、
n8n 评测口径（carlosaragon.online）、2026 HITL 审批框架（agentmelt.com）、后台编码 Agent 对比（amux.io）。

## 3. 我们的形态（四档策略）

| 档位 | 触发条件 | 判什么 | 失败时 |
|---|---|---|---|
| **L1 全量** | 定时任务每次都跑 | 台账对账：声称完成 vs 有证据、diff 存在性、测试是否真跑过 | BLOCK → 不宣告成功 |
| **L3 守卫** | 本轮台账里出现**对外/不可逆**动作（`git_commit`/`git push`/`mcp__*`/`scheduled_create`/破坏性 shell） | 独立 verifier turn 复核证据是否支撑结论 | FLAG 或没跑成 → 不宣告成功 |
| **L3 抽样** | 5%（`DEFAULT_SAMPLE_RATE`） | 同上，仅用于**度量**低风险任务的判定质量 | **不降级**（抽样是测量，不是守卫） |
| **L3 复核 BLOCK** | 显式 `onBlock: true`（默认关） | 为 L1 的 BLOCK 补一份理由，供人看 | 不推翻 BLOCK |

两条关键取舍：

- **L1 BLOCK 不被 L3 推翻。** 确定性对账（"声称写了但没有任何证据"）不是概率问题，
  让模型翻转它等于把确定性问题变成掷骰子。L3 只能往 annotation 里补理由。
- **抽样的 FLAG 不降级交付。** 抽样是为了拿指标，如果它也能否决交付，等于 5% 的任务
  随机因为一次模型噪声而失败 —— 那是把度量工具变成了随机故障源。

## 4. 实现映射

| 文件 | 职责 | 关键符号 |
|---|---|---|
| `main/verifyPolicy.js`（新增，纯函数） | 何时值得花钱、判完敢不敢宣告成功 | `hasRiskyAction` / `shouldRunL3` / `decideDelivery` / `shouldAutoPause` |
| `main/scheduledVerify.js`（新增） | 把策略接到 `createVerificationRun` 上 | `createScheduledVerify` → `{onTrace, onToolCall, finish}` |
| `main/verifyRun.js` | 判定引擎（不知道「何时跑」，只接收闸门） | `runVerification({ l3Gate })`、`createVerificationRun({ l3Gate })` |
| `main/main.js` | 装配：台账桥接 + L3 评审目标（优先 compact 档） | `runScheduledAgentTask`、`scheduledL3Target` |
| `main/scheduler.js` | 交付裁决 + 任务级熔断 | `run.verify`、`t.fail_streak`、`t.auto_pause_reason` |

设计边界：**策略与引擎分离**。`verifyRun` 只管「怎么判」，`verifyPolicy` 只管「何时判、判完算不算数」。
这样两条通道（主对话 / 定时）能用不同口径而不复制判定逻辑，策略也能纯 Node 单测。

## 5. 失败语义：两条通道唯一必须分叉的地方

| 场景 | 主对话（有人值守） | 定时任务（无人值守） |
|---|---|---|
| L3 没跑成（no_chat / 超时 / 解析失败） | 放行（fail-open） | **不宣告成功**（fail-closed），产物仍归档 |
| 守卫型 L3 判 FLAG | 尾部追加提示，照常交付 | **不宣告成功** |
| L1 BLOCK | 追加对账提示 | **不宣告成功** |
| 闸门判定「不值得跑 L3」 | 不适用 | 正常交付（这是省钱，不是未验证） |

落点：`run.status = 'failed'` 且 `run.error = '未通过交付校验：…'`，同时在运行记录里写
`run.verify = { level, verdict, reason, annotation, l3 }` —— 无人值守下这是唯一能回答
「这次到底判过没判、判成什么」的地方（定时通道没有 `agent:event`，不广播事件）。

## 6. 成本模型

设任务每次运行触发 L3 的概率为 `P`：

```
P = 1 − (1 − 有对外动作的概率) × (1 − 0.05)
```

| 任务形态 | 有对外动作 | P | 每天 24 次跑的额外调用 |
|---|---|---|---|
| 只读汇总（抓新闻、读库出报表） | 否 | 5% | ≈ 1.2 次 |
| 编码类（改文件 + 提交） | 是 | 100% | 24 次 |
| 混合（偶尔提交） | 30% | 33.5% | ≈ 8 次 |

L3 单次成本：输入 ≤20k 字符（台账末 60 条 + 回答 12k，逐级缩字段）+ 输出 ≤1.2k tokens。
默认走 **compact 档模型**（设置页的「任务分档模型」），未配置时回落主模型。
换来的是一条硬保障：**有对外动作的无人值守任务，不会在没人看着的时候"自述完成"**。

## 7. 任务级熔断

连续失败（含被降级交付）达 3 次 → 自动暂停任务，写
`t.auto_pause_reason`，UI 卡片直接展示「已自动暂停：…」。

- 只对**自动触发**（`scheduled` / `catchup`）计数：用户手动点「立即运行」失败三次
  是在排查问题，不该把任务停掉。
- 判据是纯函数 `shouldAutoPause`，阈值非法时回落 3（不因配置错误把任务永久停摆）。

## 8. 待确认动作清单（产物形态即校验）

事后判分能拦住「宣告成功」，拦不住**已经推出去的 commit / 已经发出去的消息**。
所以定时通道加了一层**事前拦截**（`main/scheduledGuard.js`）：

| 动作 | 定时任务默认 | 理由 |
|---|---|---|
| `gitCommit` / `gitAdd` | **拦** | 提交对外可见；无人值守没有人能批准 |
| `mcpCallTool` | **拦** | 外部服务的读/写无法从工具名可靠区分 |
| `prReview` / `prComment` | **拦** | 对他人仓库/PR 的可见动作 |
| `shell` 含 push/rm/对外写 | **拦** | 破坏性或对外，不可回滚 |
| `writeFile` / `editFile` / `applyPatch` | 放行 | 这是任务产物本身，拦掉任务就没法干活 |
| 读 / grep / glob / git 只读 / PR 只读 | 放行 | 无副作用 |

被拦时：
1. **下游实现一次都不执行**（动作真的没发生），返回结构化失败
   `{ ok:false, blocked:true, error:'SCHEDULED_BLOCKED: …请勿重试…' }` ——
   提示模型改写摘要而不是换法子重试（否则预算全烧在同一个动作上）。
2. 记入待确认清单（同一动作重试多次只记一条，`gitCommit` 连 `-m "…"` 一起记，人能照着敲）。
3. 清单随运行记录落到 `run.pending_actions`，并写进归档 md 的「待确认动作（N 项，本次未执行）」小节，
   任务卡片显示「待确认 N 项」。

任务级放行：`task.external_policy === 'allow'` 时整层不启用（当前只能由数据层设置，
UI 开关尚未提供）。
