## 2. 问题清单

### P1-1　无人值守路径的审批档取自"最后一次交互"，不是用户设置

| 项 | 内容 |
|---|---|
| **现象** | 编排组快照、定时任务、CUA/回放、Worker 兜底，四处都调 `agentRunner.getCurrentApprovalMode()`。该函数返回模块级变量 `currentUserApprovalMode`，而它只在 `startAgentRun` 里被赋值 |
| **证据** | `main/agentRunner.js:46`（`let currentUserApprovalMode = 'on-request'`）→ `:90`（每次 run 覆盖）→ `:380`（`getCurrentApprovalMode: () => currentUserApprovalMode`）；消费点：`main/main.js:820`（编排组 `hostPolicySnapshot`）、`:956`（定时任务）、`:1314`/`:1394`（CUA run / 回放）、`:1058` → `main/workerPool.js:210`（Worker 兜底） |
| **为什么它是错的** | 审批档**可以按会话覆盖**：`renderer/src/hooks/useAgentRun.ts:527` 是 `thread?.approval_mode \|\| approvalSettings?.approval_mode \|\| 'on-request'`。于是「全局最后一次 run 的档」≠「发起本次编排/当前用户设置」 |
| **后果** | ① 用户在会话 A 设 `always`（每条都问），在会话 B 发过消息（`never`），之后在 A 发起编排 → 组快照记成 `never`，Worker 按 `never + auto-safe 地板` 跑，**比用户设置更松，且无任何提示**；② 定时任务在用户从未发消息的进程里，档位退回默认 `on-request`，用户在设置里选的 `always` 被丢弃 |
| **修法** | 把"档位"从"进程级最后值"改成两个明确来源：<br>① **交互 run**：`agent:run` 的 `payload.approvalMode`，只在本次 run 内有效（已有，无需改）；<br>② **无人值守**（定时任务/CUA/Worker 兜底/编排组快照）：读**持久化设置** `localStore.preferences.approval_mode`，缺省 `on-request`。<br>编排组创建时，把"发起该组的那次 run 的档"作为显式参数传下去，不要从全局读 |
| **改动面** | `main/agentRunner.js`（删 `currentUserApprovalMode` 或改为 `Map<runId, mode>`）、`main/main.js` 5 处消费点、`main/approvalPolicy.js` 加 `resolveApprovalMode({ runId, fallbackToSettings })` |
| **验收** | 新增测试：① 两个会话不同档位，A 发起编排时组快照 = A 的档；② 无任何交互 run 时，定时任务档 = 设置里的档；③ `stricterApproval` 地板不变 |

### P1-2　服务端模型代理无 SSRF 防护

| 项 | 内容 |
|---|---|
| **现象** | `POST /api/chat` 用数据库里的 `base_url` 直接 `fetch`，无协议白名单、无内网地址拦截、无重定向复检 |
| **证据** | `server/src/routes/chat.js:32` `fetch(\`${baseUrl}/chat/completions\`)`；`baseUrl` 来自 `:19` 查出的 `model_providers.base_url`（用户可填）。全仓 `grep 169.254\|isPrivate\|privateIp` **零命中** |
| **后果** | 云端部署时，攻击者把自己的 provider `base_url` 填成 `http://169.254.169.254/latest/meta-data/`（或内网服务），服务端发起请求并把响应回传（见 P2-1），等于**用服务端做内网探针 + 数据外带**。桌面端形态不受影响（用户自己的机器） |
| **修法** | 在 fetch 前加 `assertSafeUpstream(url)`：① 只允许 `http:/https:`；② 解析主机名后拒绝私有网段（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`::1`、`fc00::/7`、`fe80::/10`）；③ `redirect: 'manual'` 或对每个跳转目标复检；④ DNS 解析结果与连接目标一致性检查（防 rebinding，可用 `undici` 的 `lookup` 钩子） |
| **改动面** | 新增 `server/src/lib/urlGuard.js`；`chat.js` 两处 fetch 前调用 |
| **验收** | 单测：`http://127.0.0.1`、`http://169.254.169.254`、`file://`、`http://[::1]`、解析到私网的自定义域名，全部拒绝并返回 400 |

### P1-3　Linux 沙箱 140 行零测试，且 CI 从不跑 Linux 真机

| 项 | 内容 |
|---|---|
| **现象** | `main/sandboxLinux.js`（140 行，bwrap 参数拼装）**不被任何测试引用**；`sandbox-crossplatform.test.js` 在非 Linux 上打印"本节未执行"（本轮实测同样 skip） |
| **证据** | `grep -rn sandboxLinux main/ test/` → 只有 `main/sandbox.js:196` 一处 require；`npm test` 输出 2 条 skip 记账 |

| **改动面** | `test/sandbox-linux.test.mjs`（新增）、`sandbox-crossplatform.test.js`（skip 条件收紧）、`ci.yml`、README |
| **验收** | 全量套件数 126 → 127；Linux CI job 绿 |

### P3-1　`file:preview` 可读任意本机路径，威胁模型未登记

| 项 | 内容 |
|---|---|
| **现象** | `previewTool.handleFilePreview` 只做 `resolveToolPath(p, cwd)`，无根目录白名单；小文件直接回 `dataUrl` |

### P3-2　三份 process host 同构不同策，缺"策略差异"守护

| 项 | 内容 |
|---|---|
| **现象** | `codeProcess/host.js`、`cuaProcess/host.js`、`browserProcess/host.js` 各 149–157 行，14 行窗口有多组完全一致；但**策略相反**：code 不重启（状态丢失），cua 重启 1 次，browser 另一套 |
| **判断** | **不建议合并**——合并会把"必须不同"的策略揉进一个开关，正是 P0 事故的温床。需要的是**把差异写成断言** |

| **验收** | 3 条新测试；`code-mode`/`cua-process`/`browser-process` 套件各 +1 |

## 4. 建议的修复顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **第一批** | P1-1（审批档来源）、P1-2（SSRF）、P1-3（Linux 沙箱） | 前两条是"静默降级/越权"，出事时用户完全无感；第三条决定对外能不能宣称 Linux 隔离 |
| 第二批 | P2-1、P2-2 | 与第一批同文件/同链路，顺手补齐 |
| 第三批 | P2-3、P3-2 | 类型与策略契约，属结构性投入，需单独排期 |
| 随时 | P3-1（文档登记） | 零成本 |

**一条低成本防回归**：给"新增空 catch"加 lint 规则——`catch` 块允许为空**仅当**同行有注释，否则报错。这样既不动存量 136 处（它们有注释），又能拦住新债。

```js
// eslint.config.mjs 建议片段（no-empty 的例外需要注释，用自定义规则或 no-empty + 注释检测）
'no-empty': ['error', { allowEmptyCatch: false }],
// 存量 136 处已带注释，若直接开会红；建议先加 // eslint-disable-next-line 批量标注，
// 或改用 `no-empty` + `reportUnusedDisableDirectives` 观察一版再收紧。
```
